# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- [mydesk.md](mydesk.md) — the original Russian-language spec ("ТЗ") for the project. Source of truth for requirements; read it when a feature's intent is unclear. (The **UI itself is English** — the spec is just the original design doc.)
- [app/](app/) — the implementation: a Vite + React + TypeScript single-page app. Most commands below are run from `app/`.
- [server/](server/) — a local Node/Express/TypeScript backend. Started as a small proxy for exactly one reason (holding the Zadarma API secret outside the browser bundle — see "Zadarma Calls tab" below), it has since grown a second, larger reason to exist: the LinkedIn Automation feature (see its own section below) needs real server-side persistence (`better-sqlite3`) and drives Playwright browser automation, neither of which can happen in the browser. A third small piece, the SMS inbox (see its own section below), also needs a server-side webhook receiver for the same "has to work whether or not a browser tab is open" reason.

This repo is a git repository at the top level (branch `main`).

## Commands (run from `app/`)

```bash
npm install       # install dependencies
npm run dev       # start Vite dev server (http://localhost:5173)
npm run build     # tsc -b type-check, then production build to app/dist
npm run lint      # ESLint
npm run preview   # serve the production build locally
```

There is no test suite yet (no test runner is configured). Type-checking (`tsc -b`, run as part of `npm run build`) and `npm run lint` are the available correctness checks.

**`server/` is now required for the app to work at all, not just the Calls tab** — since the table/CRM data migration (see "Persistence — table/row data lives server-side" below), the main Table view itself talks to `server/` for every table/row read and write. Needs a second process alongside `npm run dev` in `app/`. In a separate terminal: `cd server && npm install && npm run dev` (binds `127.0.0.1:4000` only by default, watches via `tsx`; set `HOST=0.0.0.0` to make it reachable from another device on the same wifi, e.g. a phone — see the table-data section below). `server/.env` holds `ZADARMA_API_KEY`/`ZADARMA_API_SECRET`/`PORT`/`ZADARMA_CALLER_NUMBER` plus `OPENAI_API_KEY` (contact-paste cleanup + call summary), `ELEVENLABS_API_KEY` (transcription — see the transcription section below; the key needs the "Speech to Text" permission enabled on the ElevenLabs dashboard), and `AUTH_USERNAME`/`AUTH_PASSWORD`/`AUTH_RECOVERY_PASSWORD`/`AUTH_TOKEN_SECRET` (the login gate — see its own section below; every route except `/health` and `/api/auth/login` 401s without a valid session token) — copy `.env.example` and fill in real values, gitignored, never commit it. Statistics/recording work with just the Zadarma vars; transcription additionally needs a valid, correctly-scoped `ELEVENLABS_API_KEY`. If `server/` isn't running, the Calls tab shows a "Could not reach the local Zadarma proxy — is it running?" toast rather than failing silently. `cd server && npm run typecheck` for its own type-check (no lint/test setup there — it's small enough that `tsc --noEmit` is the only correctness check).

**Running the LinkedIn tab**: same `server/` process as above, plus one extra manual step — launch Chrome with remote debugging enabled *before* opening the tab, pointed at a **separate, dedicated profile directory**, not your default one: `open -na "Google Chrome" --args --remote-debugging-port=9222 --user-data-dir="$HOME/.mydesk-linkedin-chrome-profile"` (`server/.env`'s `LINKEDIN_CDP_URL` only needs setting if you're not using the 9222 default). **The `--user-data-dir` isn't optional** — confirmed live on Chrome 151.x, launching against the *default* profile silently never opens the debug port at all (no error, it just isn't listening), a deliberate Chrome security hardening against outside tools attaching to your main, cookie-holding profile. **The `-n` isn't optional either, and is easy to forget** — confirmed live: if your regular Chrome (any profile) is already running at all, plain `open -a` just tells that already-running instance to open a new window and silently ignores the new `--args` entirely (Chrome only applies command-line flags on the very first launch of the app); `-n` forces a genuinely separate process so the flags actually take effect. That dedicated profile starts empty — log into LinkedIn in it once, then keep relaunching against the *same* directory every time so it stays one real, warm, persistent session (cookies persist on disk, so it survives the automation Chrome window being closed/crashing and relaunched — see `browser.ts`'s own doc comment and the LinkedIn Automation section below for why that matters).  Registering the SMS webhook (SMS inbox tab's "⚙️ Registruoti SMS webhook" button) additionally needs `PUBLIC_BASE_URL` set to a real, publicly reachable URL — it only works end-to-end once actually deployed somewhere Zadarma can reach, not against `localhost`.

Node 20.9 is the environment this was scaffolded with; `create-vite@latest`/some newer dev-tooling requires Node ^20.19 — if `npm create vite@latest` fails with a `styleText` export error, pin an older `create-vite` version (e.g. `npm create vite@6`) or upgrade Node.

**Testing clipboard/copy-paste in headless browsers**: headless Chromium does not reliably wire `Ctrl+C`/`Ctrl+V` keypresses to real `copy`/`paste` DOM events (no OS-level clipboard integration without a real display). This is a harness limitation, not an app bug — real desktop browsers dispatch these events normally. To verify paste logic under Playwright, dispatch a synthetic event instead of pressing keys:
```js
await page.evaluate((tsv) => {
  const dt = new DataTransfer();
  dt.setData('text/plain', tsv);
  document.dispatchEvent(new ClipboardEvent('paste', { clipboardData: dt, bubbles: true, cancelable: true }));
}, 'A1\tB1\nA2\tB2');
```

## Product context

A minimalist "CRM" that is really an Excel-style spreadsheet for cold-calling, plus a calendar/task list — explicitly **not** a pipeline/deal-stage/kanban CRM. One row = one company. Full spec: [mydesk.md](mydesk.md).

Platform: originally a **local web app** with all table/CRM data client-side in IndexedDB and no backend at all — that was true right up until a real, reported problem forced a change: IndexedDB is per-browser/per-device, so opening the app on a phone showed zero of the user's ~14,000 real contacts, not a bug, just a consequence of the design. The main table/CRM data now lives server-side too (`server/src/tableData/db.ts`) — see "Table/CRM data storage" in the architecture section below for the full migration. CSV is still the cross-*table-format* import/export mechanism (Excel round-tripping, backups), just no longer the only way data gets from one device to another. The Calls/LinkedIn/SMS tabs already had their own server-side reasons to exist (see their own sections below) — this migration is a separate, later addition to the same `server/` process, not a new pattern.

New tables (including the very first one, auto-created on a fresh install) start with **zero columns** — there is no default seed schema. `TableView` shows a "no columns yet" empty state (with a working "+ Add a column" link — see the right-click-menus section below for why that needed its own entry point) until the user adds one, or imports a CSV.

## Architecture (`app/src/`)

The app is a **workspace of multiple named tables** (Workspace screen → pick/create a table → work in it), not a single global table. Two Zustand stores split that responsibility along the same line:

- `useWorkspaceStore` ([store/useWorkspaceStore.ts](app/src/store/useWorkspaceStore.ts)) owns the list of tables (`TableMeta { id, name, columns, createdAt, updatedAt }`) and which one is active. It persists the active table id to `localStorage` (not IndexedDB — it's a plain string, and this is what makes the app reopen on the same table the user was last in).
- `useTableStore` ([store/useTableStore.ts](app/src/store/useTableStore.ts)) holds the **currently loaded table's** `columns` and `rows` and is the only thing table/calendar components read or write through.

**`loadTable` always re-fetches the table fresh from IndexedDB by id — never from `useWorkspaceStore`'s cached copy.** This fixed a real bug: `useWorkspaceStore.tables[i].columns` is a snapshot taken at workspace-load time and is never updated when `useTableStore` edits columns (only the IndexedDB record is). Passing that stale `TableMeta` object into `loadTable` on re-entry made deleted columns appear to "come back" after leaving and re-opening a table. `App.tsx`'s effect now depends on `activeTableId` (a string) and calls `loadTable(activeTableId)`, which does its own `getTable(id)` read. If you add more per-table fields, keep this "always re-read on load" rule — don't thread cached `TableMeta` objects between the two stores.

**Data model** ([types.ts](app/src/types.ts)):
- `Column { id, name, type, options?, optionColors?, isNextActionDate?, width? }` — `type` is one of `text | phone | company | note | contact | dropdown | date`. `company` is a plain single-line value like `text`/`phone` (same edit UX) but is what `getPrimaryLabel()` (`utils/row.ts`) looks for first when it needs "the" label for a row — see below. `options`/`optionColors` only apply to `dropdown` (`optionColors` maps an option's string value to a hex color for its colored badge/select background). At most one `date` column per table should have `isNextActionDate: true` — that's the column the calendar/task list reads from. `width` is in pixels, user-resizable, falls back to `DEFAULT_COLUMN_WIDTH`.
- `Row { id, tableId, cells: Record<columnId, string>, colors?, order, height?, createdAt, updatedAt }` — cell values are strings regardless of column type. A `date`-type value is either a bare `yyyy-MM-dd` or, if the user opted into a specific time for that one row, `yyyy-MM-ddTHH:mm` (see "Optional time" below). `colors` maps a column id to a hex background color for that cell (independent of the column's dropdown `optionColors`). `order` is a sequential integer reassigned across *all* of a table's rows on every manual drag-reorder. `height` is in pixels, user-resizable, falls back to `DEFAULT_ROW_HEIGHT`.

**Persistence — table/row data lives server-side** ([db/db.ts](app/src/db/db.ts) on the frontend, [server/src/tableData/db.ts](server/src/tableData/db.ts) on the backend): originally a thin `idb` (IndexedDB) wrapper end-to-end, migrated to a real server (`better-sqlite3`, same established pattern as `linkedin.sqlite`/`sms-inbox.sqlite` — lazy-singleton connection, one `migrate()` exec block, camelCase-interface/snake_case-Row-interface/`xFromRow()` mapping, `server/table-data.sqlite`, gitignored) after a real, reported problem: IndexedDB is per-browser/per-device, so a user with ~14,000 real contacts on their Mac's browser opened the app on their phone and saw zero — not a bug, just what "all data stored client-side" actually means once more than one device is involved. **The migration only touched `db/db.ts` itself** — `useTableStore.ts`/`useWorkspaceStore.ts` (the two Zustand stores owning all table/row state, ~32 and ~6 actions between them) never touched IndexedDB directly to begin with, only ever called through `db.ts`'s named exports (`loadTables`, `saveTable`, `getTable`, `updateTableColumns`, `updateTableName`, `deleteTableDB`, `loadRowsForTable`, `saveRow`, `saveRows`, `deleteRowDB`, `countRowsForTable`) — rewriting those ~11 functions' bodies from `idb` calls to `localApiRequest` calls against the new `/api/tables`/`/api/rows` routes (same auth-gated, `asyncHandler`-wrapped pattern every other server route uses) left both stores completely unchanged, confirmed by a clean typecheck with zero edits to either file. Server-side schema is a JSON-blob design (`cells_json`/`colors_json` TEXT columns), not EAV — it mirrors the client's own already-opaque `Record<string,string>` cell storage exactly, rather than normalizing into a per-cell table. `saveRows()` stays a **single bulk endpoint** (`PUT /api/rows`, one SQLite transaction) on both ends, not one-row-at-a-time — `moveRows`/`insertRows`/`applySortOrder` in `useTableStore.ts` all rewrite `order` across *every* row in the table on one drag-reorder or column-sort click, so a 14,000-row table doing that as 14,000 separate HTTP requests would be unusable; this was the one performance detail that mattered enough to design around up front. `updateTableColumns()`/`updateTableName()` still do a server-side read-modify-write instead of a blind overwrite, for the identical stale-copy reason as before (`useWorkspaceStore` and `useTableStore` each hold their own in-memory copy of a table's `columns`/`name`) — keep this pattern for any new field both stores might touch. The old IndexedDB `tables`/`rows` object stores are still declared in `db.ts` and readable via `loadTablesFromIndexedDB()`/`loadRowsForTableFromIndexedDB()` — deliberately kept, under deliberately different names so nothing accidentally reads local instead of server data — purely so the one-time **migration action** ([utils/migrateTableData.ts](app/src/utils/migrateTableData.ts), a "⬆ Perkelti į serverį" button on the Workspace screen) can move whatever old local data still exists up to the server; it's a plain upsert keyed by the same ids, safe to re-run, and never deletes the local copy. Reachability for a phone follows the same rule as any other device on this app: either the same wifi as wherever `server/` is running (with `HOST=0.0.0.0` so it isn't `127.0.0.1`-only, and the frontend's `VITE_API_BASE_URL` pointed at that machine's LAN IP — see `app/.env.example`), or the real public deployment. No offline queue or conflict resolution was added — writes are still fire-and-forget same as before, just over the network instead of to local disk, so a real network failure now matters more than a local IndexedDB failure ever did; this was a deliberate, accepted scope cut, not an oversight.

**This migration also made `server/` being down a whole-app failure, not just a Calls-tab one — `useWorkspaceStore.init()` needed its own error handling to avoid an infinite, unexplained "Kraunama…" spinner.** Before this migration, `init()`'s `loadTables()` call was a local IndexedDB read that essentially never threw; after it, that same call is a network request that fails outright whenever `server/` isn't reachable (not running, wrong `VITE_API_BASE_URL`, phone off the Mac's wifi). An unhandled throw there left `set({..., ready: true})` never executing — `App.tsx`'s `!workspaceReady` branch has no timeout and no error path, so the user would sit on "Kraunama…" forever with zero indication anything was wrong, a real regression this migration introduced since only the Calls tab had this class of degraded-but-informative failure before (its own "Could not reach the local Zadarma proxy — is it running?" toast). Fixed by wrapping `init()`'s body in try/catch: on failure it sets a new `initError: string | null` field instead of leaving `ready` stuck at `false`, and `App.tsx` checks `workspaceInitError` in a branch rendered before the `!workspaceReady` check, showing the error plus a "Bandyti dar kartą" (try again) button that just re-calls `initWorkspace()`. If you add another store whose `init`/load path now depends on `server/` being up, apply the same pattern — don't assume a local-storage-era assumption ("this read basically can't fail") still holds after a store's backing data moves server-side.

**All three server-side SQLite files (`linkedin.sqlite`, `sms-inbox.sqlite`, and this new `table-data.sqlite`) write through [server/src/dataDir.ts](server/src/dataDir.ts)'s `dataFilePath()` rather than a hardcoded path next to source, specifically because of this migration.** Discovered before it could bite in production, not after: Render's free tier (where `server/` actually runs — see the login-gate section's own note on this, previously only relevant because it blocks an in-app password-change flow) has an ephemeral filesystem that gets wiped on every deploy *and* on the free-tier idle-restart. That was a tolerable, accepted gap when the only thing living on local disk was LinkedIn campaign state and an SMS log — but table-data.sqlite is now the durable copy of the user's entire ~14,000-row CRM, the whole point of this migration being that it survives being looked at from a different device. Deploying it with no persistent disk would have silently reset that data on the next idle cycle, defeating the migration's own purpose. `dataFilePath(filename)` resolves against `process.env.DATA_DIR` if set, falling back to `server/` itself (unchanged behavior for local dev, where this never needs to be set) — deploying now additionally requires attaching a Render Disk and setting `DATA_DIR` to its mount path (e.g. `/data`) in Render's dashboard, documented in `server/.env.example`.

**A second, real bug found the same day, against the real production deployment**: `express.json()` (`server/src/index.ts`) had no `limit` option, so it inherited Express's built-in **100kb** default body-size cap — fine for every other route in this app, but `PUT /api/rows`'s whole point is sending an entire table's rows as one bulk JSON payload (see `saveRows()`'s own doc comment above), and a real ~14,000-row table is several MB of JSON, nowhere close to 100kb. The one-time migration action (`⬆ Perkelti į serverį`) failed against it with a raw, unhelpful "Internal server error" — confirmed live: body-parser was throwing a `PayloadTooLargeError` that the error-mapping middleware had no specific case for, so it fell through to the generic `catch-all` 500. Fixed two ways: `express.json({ limit: '50mb' })`, and an explicit check for `err.type === 'entity.too.large'` in the error middleware mapping to a real `413` with a readable message, so a future table that outgrows even that limit fails clearly instead of the same generic 500. **Root cause was purely this size cap, not the Render disk/`DATA_DIR` work done earlier that same session** — worth keeping separate in mind if a future "migration failed" report comes in, since the two land at completely different fixes.

A third, tiny Zustand store ([store/useToastStore.ts](app/src/store/useToastStore.ts)) drives a single global toast notification.

**The 32,767-char Excel cell limit** is enforced in exactly one place, [utils/cellLimit.ts](app/src/utils/cellLimit.ts)'s `clampToLimit()`, called from `updateCell`, `updateCells` (batched writes — see paste, below), and `importCsvRows` in `useTableStore`. Don't duplicate this check elsewhere — route all cell writes through the store.

**CSV import goes through an explicit per-column mapping step, not silent auto-matching** ([components/Table/CsvImportMapping.tsx](app/src/components/Table/CsvImportMapping.tsx)). This replaced an earlier version that matched headers by name case-insensitively and *always* created any unmatched header as a new `type: 'text'` column, no exceptions. That was a real, reported bug: `note`/`contact` columns store their cell value as a JSON array (see below), and exporting one of those columns then re-importing the CSV into a context where a same-named, correctly-typed column didn't already exist (a fresh table, a renamed column, a different workspace) silently created a plain-text column and displayed the raw JSON literally — "странные коды" (garbled codes) from the user's report. `parseCsvFile` still just parses; `TableView`'s `handleFileChange` now stores the raw `{ headers, dataRows }` as `pendingImport` instead of calling `importCsvRows` immediately, and renders `<CsvImportMapping>` (a centered `.modal`/`.modal-backdrop` — a new pattern, distinct from the anchor-positioned `Popover`, since this needs room for a per-header list that can run long) to resolve one `ImportColumnMapping` per header before anything is written: `{ action: 'existing', columnId }`, `{ action: 'new', columnType }`, or `{ action: 'skip' }`. `importCsvRows` (`useTableStore.ts`) now takes that resolved mapping as a required third argument and just executes it — it no longer does any name-matching or type-defaulting itself. Default mapping choices (`buildDefaultMapping`, still overridable per-header before confirming): a header matching an existing column name (case-insensitive, trimmed — same rule as before) defaults to `'existing'`; an unmatched header defaults to `'new'`, with its *type* guessed by `sniffColumnType()` ([utils/csv.ts](app/src/utils/csv.ts)) sampling up to 8 non-empty cell values in that column and checking whether they parse as the `{ id, text, createdAt? }` JSON shape `utils/noteHistory.ts`/`utils/contacts.ts` serialize — a numeric `createdAt` on every entry means `note`, its absence means `contact`, neither means `text`. This is a default suggestion only, not a re-parse of the data itself; the user still reviews/adjusts the mapping modal before anything imports. Export (`exportRowsToCsv`/`downloadCsv`) is unchanged: writes all of the active table's rows (ignoring the search box), raw cell values as stored (so a note/contact column's raw JSON is what ends up in the CSV — the mapping step on the *import* side is what makes that round-trip safely, not a change to what export produces), and prepends a UTF-8 BOM so Excel opens non-ASCII content correctly.

**The calendar/task list has no independent data model** — it's a derived view over the active table's `rows`, filtered/grouped by whichever column has `isNextActionDate: true` (via `getNextActionColumn()` in [utils/row.ts](app/src/utils/row.ts)). Date comparisons (`isOverdue`/`isDueToday`/`isFuture` in [utils/date.ts](app/src/utils/date.ts)) compare only the **date part** (`getDatePart()`, first 10 chars) as plain ISO strings — never the raw cell value — because a value may carry an optional time suffix (see below) and `"2026-08-15" !== "2026-08-15T14:00"` even though they're the same day.

**Optional time on the next-action date** ([components/Table/DataCell.tsx](app/src/components/Table/DataCell.tsx) `date` branch, [utils/date.ts](app/src/utils/date.ts)): the date input stays the default, single-click interaction; a small 🕐 button (shown only once a date is set) reveals a second `<input type="time">` inline, and the cell's stored value becomes `combineDateTime(date, time)`. This is deliberately per-row opt-in, not a column-level setting — most rows never touch it. `TaskListView`/`CalendarGridView` both read `getTimePart()` to show the time when present (calendar day chips prefix it, e.g. "14:30 Acme Inc") and sort entries within the same day by the raw value (bare dates sort before same-day timed ones, since a shorter string that's a prefix of a longer one sorts first lexically). `TaskListView` rows are deliberately minimal — company label ([utils/row.ts](app/src/utils/row.ts) `getPrimaryLabel`), date/time, and an "Open in table →" button, nothing else (no status badge, phone, or note preview); it's meant as a quick call queue, not a row preview.

**Optionally linking a specific contact to the next-action date** — a 👤 button sits next to the 🕐 one (same gating: only shown once a date is set), opening a `Popover` listing that row's `contact`-type column entries (`parseContacts`), letting you pick which person this date/call is actually for — entirely optional, most rows never set one. Stored as `Row.linkedContactId` ([types.ts](app/src/types.ts)) — a plain **row-level** field, not keyed by column id, because there's only ever one next-action-date column per table (`isNextActionDate`) and only one `contact`-type column in practice, so there's nothing to disambiguate. `useTableStore.setLinkedContact(rowId, contactId | null)` writes it (`snapshot()` + `saveRow`, same pattern as every other row mutation). `getLinkedContactName(row, columns)` ([utils/row.ts](app/src/utils/row.ts)) resolves it to a display name — finds the table's contact column, looks up the matching `ContactEntry` by id, and runs it through `contactTextToFields()` for "First Last"; a dangling id (the contact entry was since edited/deleted) just resolves to `null`, never an error, since notes/contacts are edited completely independently of this link. Surfaced in both calendar views: `TaskListView` shows it right after the company label as `"{company} | {contact name}"` (on request, that exact separator); `CalendarGridView`'s day chips add it to the chip's `title` tooltip rather than the visible (space-constrained, already-truncated — see `CHIP_LABEL_LIMIT`) label text.

`DataCell`'s `contactsRaw` prop (the row's raw Contacts-cell string, computed once per row in `TableView` via `getColumnByType(columns, 'contact')`, not per cell) is what the date cell's picker reads — and **it had to be added to the memo comparator** alongside `highlightQuery`, for a subtler reason than that one: it's derived from a *different* column than the one this particular `DataCell` instance's own `column` prop refers to (the row's Contacts column, not whatever column this cell renders), so neither `row` nor `column` staying referentially equal guarantees `contactsRaw` did too — e.g. adding a Contacts column to a table that already had next-action dates set wouldn't otherwise be picked up until some unrelated prop changed too.

**`CalendarGridView`'s day cells needed an explicit `min-width: 0`, twice.** Grid/flex items default to `min-width: auto`, which sizes to their widest *unbreakable* line of content — one chip holding a long, space-less company name (a real support case: a 50-character name with no spaces) was enough to force that `.calendar-day` grid item wider than its `1fr` track, blowing out all 7 columns of the whole month grid. `min-width: 0` is set on both `.calendar-day` (the grid item) and `.calendar-day-tasks` (the flex item nested inside it) — CSS's default min-size floor has to be overridden at *every* flex/grid level between the grid and the overflowing text, not just the outermost one, or the inner container still forces its parent wide. `.calendar-chip` itself also truncates its label to `CHIP_LABEL_LIMIT` (15) chars with an ellipsis before render (`truncateLabel()` in `CalendarGridView.tsx`) — belt-and-suspenders with the CSS fix, and also just keeps the calendar readable with normal-length names. The full label is still available via the chip's `title` attribute (native tooltip).

**Popovers render through a portal** ([components/Popover.tsx](app/src/components/Popover.tsx)): takes the trigger's `HTMLElement` directly (captured into a local `const` in the click handler — see the note on stale event targets below), renders into `document.body` via `createPortal`, computes `position: fixed` from `getBoundingClientRect()` clamped to the viewport. This avoids the popover being clipped or pushed off-screen by the table's `overflow: auto` scroll container or its `position: sticky` header. React's synthetic event bubbling still runs through the *component* tree for portaled content, so "click anywhere in `.table-view` closes open popovers" keeps working unchanged.

**Don't read `event.currentTarget`/`event.target` inside a `setState` updater callback.** React nulls out a SyntheticEvent's fields once the event finishes dispatching, and an updater function (`setX(prev => ...)`) can run later than that. This caused a real, intermittent bug: the column-menu and add-column trigger buttons captured `e.currentTarget` *inside* the updater passed to `setOpenMenu`/`setAddColumnAnchor`, which sometimes resolved to `null` and crashed `Popover`. Fixed by extracting `const anchor = e.currentTarget` as a plain variable *before* calling `setState`, then closing over that variable. The same class of bug bit the column/row resize handlers a different way: `handleUp` needs the *latest* live width/height, but reading it via `setResizingColumn(prev => { sideEffect(prev); return next })` — calling another store action from inside an updater — trips React's "Cannot update a component while rendering a different component" warning, because updaters are supposed to be pure. Fixed by tracking the live value in a `useRef` (updated on every `mousemove`, always current, no re-render) and calling `setColumnWidth`/`setRowHeight` directly in `handleUp` as an ordinary side effect, with `setResizingColumn(null)` as a separate, pure update. Follow this ref-based pattern for any new drag-to-resize/drag-to-adjust interaction rather than reaching for a "read-and-side-effect" updater.

**`text`/`phone`/`company` cells are single-click-to-edit, autosaving, and only ever one live `<input>` at a time** ([components/Table/DataCell.tsx](app/src/components/Table/DataCell.tsx)). A cell renders as a plain truncating `<button>` until it becomes the table's one `activeCell`; `TableView` passes that down as the `editable` prop, and only the currently-`editable` cell swaps to a real `<input autoFocus>` — every other cell, even in the same column, stays a button. This is deliberate, not incidental: an earlier version made *every* cell a permanently-live `<input>`, and that captured trackpad horizontal-scroll deltas as internal text-scrolling instead of letting them bubble to the table's scroll container. `dropdown` (`<select>`) and `date` (`<input type="date">` [+ optional `time`]) don't have that failure mode and stay as always-interactive native controls regardless of `editable`. `editable` requires *both* `activeCell` to match *and* `isSingleCellSelection` (`rangeAnchor.r === rangeFocus.r && rangeAnchor.c === rangeFocus.c`) — see the selection-systems section below for why a multi-cell drag must never leave its last cell in edit mode.

A cell's custom background color (`row.colors[column.id]`) is an inline style — and it has to be set on the *interactive element itself* (the `<input>`/`<select>`/date `<input>`), not just the `<td>`, or it visibly disappears the moment the cell is focused: `.cell input:focus, .cell select:focus { background: var(--bg) }` in `App.css` unconditionally paints an opaque background on focus (so an uncolored cell being edited reads clearly against the zebra-striped rows behind it), and since a click now enters edit mode immediately, that rule was winning almost every time a colored cell was touched. Inline `style={{ backgroundColor: color }}` on the input beats a class-based `:focus` rule regardless of specificity, so setting it there (in addition to the `<td>`, for the non-editable/button state) makes the color survive editing too. The *selected/in-range* highlight uses `outline`/`box-shadow` instead of `background` so it never overrides a custom color either.

For the non-editable **plain-button** preview, the color-safe hover handling took three attempts to actually land, because each fix addressed a real but incomplete cause and the bug kept resurfacing under slightly different conditions. `cell-preview-hoverable` is conditionally added to the button only when there's *no* custom color — the intent being "no class, no hover rule, no gray." But a *global* `button:hover { background-color: var(--bg-hover) }` reset in `index.css` (element + pseudo-class, specificity `0,1,1`) actually outranks the plain `.cell-preview` rule's `background: transparent` (one class, `0,1,0`) the instant `:hover` is involved — so omitting `cell-preview-hoverable` was never enough on its own; every `.cell-preview` button greyed out on hover via that global rule regardless, including colored ones. This slipped past two rounds of verification because those checks read the `<td>`'s computed background (which never changed — its inline color was never in question) rather than the child `<button>`'s (which did change, and is what's actually visible, since the button fills the cell). The real fix is an explicit `.cell-preview:hover { background: transparent }` (one class + pseudo-class, `0,2,0` — beats the global rule outright), declared immediately before `.cell-preview-hoverable:hover` (same specificity, so source order settles the tie in its favor for buttons that carry both classes). If you add another interactive element that reuses global `button`/`input`/`select` base styles inside a colored cell, check whether a bare pseudo-class in `index.css` can similarly outrank a single-class override in `App.css` — same trap. The dropdown `<select>` sidesteps this differently: it sets its background inline (preferring the selected option's own badge color from `optionColors`, falling back to the cell's generic fill color), the same "inline wins regardless of specificity" approach as the `:focus` fix above.

Zebra striping and row-hover are also **per-cell, not `<tr>`-level, for the same color-safety reason.** They used to be a plain `table.sheet tbody tr:nth-child(even) { background }` / `tr:hover { background }`, relying on every browser correctly implementing the CSS table background-painting order (cell backgrounds layer above row backgrounds) to keep a colored `<td>`'s own background showing through. Rather than depend on that, `DataCell.tsx` adds a `cell-row-bg` class to a cell's `cellClassName` *only* when it has no custom color, and the CSS selectors were rescoped to `tr:nth-child(even) td.cell-row-bg` / `tr:hover td.cell-row-bg` — a colored cell is structurally outside those selectors, so there's nothing relying on paint order for it to break: the rule simply never targets it, in any browser.

Autosave here needs **two** commit paths, not just `onBlur`, because of a real race: clicking a *different* cell fires that cell's `onSelect`, which flips `activeCell` and re-renders — and because `editable` becoming `false` unmounts this cell's `<input>` in that same render pass, the unmount can beat the browser's native `blur` event, silently dropping whatever was typed (this was caught by an end-to-end test, not code review — the input showed the typed value right up until the click, then the cell reverted to blank). The fix: `commitRef` holds the latest commit closure (reassigned on every render, so it's never stale), and a `useEffect(() => { if (!editable) return; return () => commitRef.current(); }, [editable])` fires the commit from the *cleanup*, which reliably runs whenever `editable` flips to `false` — regardless of whether a native blur happened first. The plain `onBlur={commit}` stays too, for the cases where `editable` *doesn't* change (Enter key, clicking the search box or toolbar) and the effect-cleanup path never fires. `Escape` sets a `skipCommitRef` flag before resetting `draft` and blurring, so the (still-current-render) `commit()` triggered by that blur discards the edit instead of saving it.

**`note` and `contact` columns expand on click, same as `text`/`phone`/`company` edit on click — just into a bigger surface instead of an inline `<input>`.** They're the two types that can hold more than fits in a line (a dated history log, a growable people list), so they get a dedicated expanded surface instead of an inline `<input>`; `text`/`phone`/`company` don't need that, single-click inline editing already covers them. **This was hover-triggered in an earlier version** (open after a short mouse-over delay, close after the mouse left both the cell and the panel for a grace period, with a focus-lock so typing didn't get interrupted by an errant mouse-leave) — reworked to click-triggered on explicit request, which is a large simplification: opening/closing a hover surface needs delay timers and a focus-lock to avoid feeling twitchy; a *click*-triggered one doesn't, because it can just reuse the same "click anywhere else closes it" mechanism every other popover in this file already uses (`closePopovers`, wired to `.table-view`'s own `onClick`). `DataCell.tsx`'s note/contact `<td>` now has an `onClick` that calls `onOpenEditor` — and it *must* call `e.stopPropagation()` first, or this exact same click keeps bubbling up to `.table-view`'s `onClick={closePopovers}`, which would clear the state this click just set, in the same batched update (this bit real: the editor silently refused to open at all until that one call was added). A genuine multi-cell drag-select is unaffected: per the note on synthetic click targets below, a click starting and ending on *different* cells never lands on either cell's own `<td>`, so it can't accidentally trigger this open handler.

- [components/Table/CellHoverEditor.tsx](app/src/components/Table/CellHoverEditor.tsx) (`note`/`contact`, name predates the click-based trigger — kept as-is rather than a churny rename) is an in-place expansion, not a positioned-below-it popup — it sits *at* the cell's own rect and auto-grows to fit content, so it reads as "the cell itself got bigger." No Save/Cancel buttons; every field autosaves (Enter or blur commits, Escape discards). Opened by `TableView`'s `openCellEditor` (sets `expandedCell`), closed by `closePopovers` (click anywhere else) or `handleCellMouseDown` (click a different cell) — the same two paths every other popover in this file already goes through, so there's no separate hover-intent timing or focus-lock machinery to maintain here anymore; the panel's own `onClick={(e) => e.stopPropagation()}` is the only thing standing between "click inside it" and "click elsewhere closes it."

**A `note`-type cell's stored string is a JSON array of dated entries, not a plain blob** ([utils/noteHistory.ts](app/src/utils/noteHistory.ts)). `parseNoteHistory()`/`serializeNoteHistory()`/`addNoteEntry()`/`updateNoteEntry()`/`removeNoteEntry()` are the only things that should touch that JSON — never read/write a note cell's raw value directly elsewhere. `CellHoverEditor`'s `'note'` mode shows a small "Add a note…" input (Enter commits a *new* entry, prepended; Shift+Enter inserts a newline within the entry being typed), a row of quick-tag buttons (`NOTE_TAGS` — "Email", "Email follow up", "Meeting", "Call follow up"; one click calls `onAddNoteEntry(tag)` directly, same as typing the tag and hitting Enter, for the handful of things actually logged constantly in a call workflow) right below it, then a most-recent-first history list, each entry timestamped via `formatHistoryTimestamp()`. Past entries *are* editable and individually removable — an earlier version made them read-only on purpose ("it's a call log, not a document"), but that was reversed on explicit request; each entry now renders as a `cell-hover-history-text-button` (click to open a `cell-hover-history-edit` textarea in its place — same Enter/blur-commits, Escape-discards pattern as everywhere else in this file, guarded by the same unmount-vs-native-blur race via a `skipNoteEditCommitRef`, see the note on this class of bug in the `text`/`phone`/`company` section above) plus a `×` remove button (`cell-hover-history-remove` — a `confirmDialog('Delete this note entry?')` guards the actual removal, added on explicit request after enough accidental note deletions; see the ConfirmDialog section below for why this isn't `window.confirm`). Editing an entry's text leaves its `createdAt` (when it was originally logged) untouched — only the text changes. `parseNoteHistory()` falls back to treating a bare string as a single undated ("legacy") entry when `JSON.parse` fails or doesn't look like an entry array, so notes written before this feature existed (or by CSV import, which just writes raw text into a note-type column) still display correctly; the first *new* entry added through the UI is what actually upgrades that cell to the JSON format going forward. The **collapsed (unopened) preview** for a note cell shows `getLatestNoteText()` (the newest entry only), not the raw JSON — if you ever see a cell rendering literal `[{"id":...` text, something is reading `row.cells[noteColumnId]` directly instead of going through this module.

**A `contact`-type cell follows a similar pattern** ([utils/contacts.ts](app/src/utils/contacts.ts)) but for a growable list of people, each just a single freeform line (`ContactEntry { id, text }` — name/phone/email all typed together, e.g. "Ivanov Ivan, +7 999 123 45 67, ivan@example.com") instead of dated free text — `parseContacts()`/`serializeContacts()`/`addContact()`/`updateContact()`/`removeContact()`, same JSON-array-with-legacy-fallback shape as notes. An *earlier* version of this column had five structured fields per contact (last/first/middle name, phone, email); `parseContacts()` still reads that old shape transparently — an entry object without a `text` field gets one synthesized by joining whichever of those five fields are present (`formatLegacyEntryText()`) — so existing data isn't lost. The storage itself has stayed one freeform string ever since that structured shape was collapsed away, but the *add/edit UI* brought the five separate fields back on explicit request — see the next paragraph. Deletion (`×` per entry) is guarded by `confirmDialog('Delete this contact?')`, same reasoning/pattern as the note-entry confirm above. The collapsed preview is `getContactsSummary()`: the first contact's full text, plus `"+N more"` if there's more than one.

**The contact add/edit UI has two parallel paths into the same freeform `text` string** (`CellHoverEditor.tsx`'s `'contact'` mode): a structured form (First name/Last name/Position/Email/Phone, five separate inputs) *and*, right below it, the original single-input "paste freeform text" field with its AI cleanup on multi-line paste (unchanged — see the next section). Both ultimately produce the exact same comma-separated shape (`joinContactFields()` in `utils/contacts.ts` builds "Name, Position, email, phone", empty fields omitted — deliberately the same field order the AI cleanup's own system prompt outputs, so `splitContactDisplayFields()` reads either origin identically) — this is a UI convenience, not a second storage format: don't be tempted to give the five fields their own storage shape, the whole point of collapsing to one string in the first place (see above) still applies. **Editing** reuses the same five-field form, pre-filled by `contactTextToFields()` — the reverse of `joinContactFields()`, necessarily a best-effort guess rather than a lossless round-trip (there's no real field boundary in a stored string, just one more application of `splitContactDisplayFields()`'s email/phone detection, plus a further guess splitting the detected "name" segment on its first space into first/last). Saving an edit requires confirming through `confirmDialog('Save changes to this contact?')` — declining leaves the edit form open with the user's in-progress (unsaved) changes still in it rather than silently discarding keystrokes; a separate "✕ Cancel" button (no confirmation needed, since agreeing to *not* save doesn't need to be confirmed) is what actually exits edit mode without applying anything, reverting to the entry's last-saved text. **Copy buttons** sit inline, directly after the phone/email field values specifically (`.cell-hover-contact-copy`, one per field that's actually present) rather than one generic per-entry copy button — requested as two distinct actions ("copy the phone" vs "copy the email"), not one.

**The 📞 call button is temporarily disabled**, not removed — `CONTACT_CALL_BUTTON_ENABLED = false` in `CellHoverEditor.tsx` gates its render (`callContact()`/`requestCallback` stay fully intact underneath, same "flag it off, don't delete it" approach as `Softphone.tsx`'s `SOFTPHONE_ENABLED`). Flip it back to `true` to restore it — nothing else needs to change.

In the expanded list, `.cell-hover-contact-field` wraps (`white-space: pre-wrap; word-break: break-word`) rather than truncating with an ellipsis — a long value (a full "name, phone, email" line before the per-field split existed) being cut off after a few characters was hiding almost all of it.

**Selection is three independent systems, not one.** Conflating them would have made a single `<th>`/gutter cell need to simultaneously start a native HTML5 drag *and* a plain-mouse drag-select, which isn't possible (once `dragstart` fires, the browser stops sending `mousemove`). So each has its own state and its own dedicated hit-target in `TableView.tsx`:
1. **Cell range** (`rangeAnchor`/`rangeFocus`, `{r, c}` indices into `filteredSortedRows`/`columns`) — drives `FormulaBar`, the copy/paste clipboard handlers, and the "🎨 Color" fill. Started by `mousedown` on any `DataCell`'s `<td>`, extended by `mouseenter` while the mouse button is down (`isRangeDragging`) or by shift+click. This is *positional*, not identity-based — sorting/filtering changes what a given `{r,c}` refers to, which is intentional (matches spreadsheet semantics of "select what's visible"). `activeCell` is just `rangeFocus` — there's no separate "which cell is active" state — which meant a real bug: dragging `B2:B11` and releasing left `rangeFocus` sitting on `B11`, and since `isRangeDragging` flips back to `false` on `mouseup`, that cell would immediately become `editable` (see the `text`/`phone`/`company` section above), stealing focus into an `<input>` — which in turn made Delete/Backspace silently do nothing, since that handler bails out whenever focus is inside a text input. `TableView`'s `isSingleCellSelection` (`rangeAnchor` and `rangeFocus` are the same `{r,c}`) gates `editable` for exactly this reason: a plain click naturally satisfies it (anchor and focus are set to the same cell in one `mousedown`, nothing ever moves them apart), but a genuine multi-cell drag never does, so the range stays selected as plain (non-focused) cells and a subsequent Delete key correctly clears the whole thing.
2. **Row selection** (`rowRangeAnchor`/`rowRangeFocus`, indices) — for bulk delete and multi-row reorder. The row-number `<span class="row-number">` handles click/shift+click/drag-select (plain mouse events); a *separate* `<span class="row-grip">` sibling is the only `draggable` element and is what native HTML5 drag-and-drop reordering hangs off of. Dragging a grip whose row is part of the current selection moves the whole set (`moveRows` in the store); dragging one that isn't first collapses the selection to just that row.
3. **Column selection** (`colRangeAnchor`/`colRangeFocus`) — the same split, mirrored for columns: `<span class="col-letter">` (click/shift+click/drag-select) vs. `<span class="col-grip">` (HTML5 drag, feeds `moveColumns`).

Row/column drag-reorder both resolve *before-vs-after* the hovered target from the cursor position relative to that target's midpoint (`dropRowIndexFromEvent`/`dropColumnIndexFromEvent`) — dropping "onto" an item without this would only ever mean "insert before it," making it impossible to drag an item past its immediate neighbor (a real bug that was caught and fixed this way; see the row-drop CSS classes `row-drop-target-before`/`-after` for the matching visual indicator). Row dragging is disabled (`rowDragEnabled`) whenever a column sort or the search box is active, since manual order and an active sort/filter both claiming to define "row position" is contradictory.

**A drag-select that starts and ends on different elements still fires a `click` on their nearest common DOM ancestor.** This is real, spec'd browser behavior, easy to forget: if `mousedown` lands on row 3's `.row-number` and `mouseup` lands on row 7's, the resulting synthetic `click` event does *not* target either `<span>` — it targets whatever DOM node contains both (in practice, something well above either element, like `<tbody>` or the `<table>`). This bit us for real: `.table-view`'s `onClick={closePopovers}` clears the just-made row/column selection (see below), and `e.stopPropagation()` on the `.row-number`/`.col-letter` elements' own `onClick` did *nothing* to stop it, because the click event's dispatch path never passes through either of those elements in the first place. The fix is `justFinishedHeaderDragRef` — the global `mouseup` handler sets it to `true` for one tick (cleared via `setTimeout(…, 0)`) whenever a row/column drag was in progress, and `closePopovers` checks it before clearing `rowRangeAnchor`/`colRangeAnchor`. If you add another "click anywhere clears X" handler, make sure it accounts for this rather than assuming stopPropagation on the drag handle is sufficient.

**Excel-style right-click menus** ([components/Table/ColumnHeaderMenu.tsx](app/src/components/Table/ColumnHeaderMenu.tsx), [RowHeaderMenu.tsx](app/src/components/Table/RowHeaderMenu.tsx), [ContextMenu.tsx](app/src/components/ContextMenu.tsx)) replaced the toolbar's old "+ Row"/"+ Column" buttons with insert-left/right, insert-above/below, delete, hide, and sort actions on the header cells themselves. `ContextMenu` is a new, minimal sibling to `Popover` — same portal-to-`document.body`/clamp-to-viewport approach, but anchored to a `{x, y}` point (the `contextmenu` event's `clientX`/`clientY`) instead of an element's rect, since a right-click menu opens at the cursor, not below a trigger button.

- **Right-clicking a column/row not already in the current selection collapses the selection to just that one first** (`handleColumnContextMenu`/`handleRowContextMenu` in `TableView.tsx`), matching Excel: right-click *inside* an existing multi-selection keeps it, so "Insert 3 columns left" applies to the whole selection, while right-clicking outside it targets just the one cell you clicked. Because this collapse-or-keep decision has to run *before* the menu opens, both handlers resolve a `targetIds: string[]` array up front and pass it straight to the menu component — `ColumnHeaderMenu`/`RowHeaderMenu` never re-derive "what's selected" themselves, they just act on `targetIds`.
- **The `.col-letter`/`.row-number` `onMouseDown` handlers needed an explicit `e.button !== 0` guard for this to work at all.** Without it, a right-click's `mousedown` (which fires before `contextmenu`, and fires for every mouse button, not just the primary one) was reaching `handleColLetterMouseDown`/`handleRowNumberMouseDown` first and collapsing the selection to just the clicked cell *unconditionally* — by the time `onContextMenu` ran, the multi-selection was already gone, so "right-click within a 3-column selection" could never see more than 1 target. This is a real instance of the same class of gotcha as the drag-select/synthetic-click issue below (an event you don't expect to reach a handler, arriving before the one you're actually trying to guard) — check `e.button` in any future header mousedown handler before assuming it only fires for left-clicks.
- **Insert position for a multi-selection is the boundary of the selection, not the specific cell right-clicked** — "insert 2 columns left" with columns B:C selected inserts before B (the leftmost), not before whichever of B/C was actually right-clicked. Both menus compute this from `targetIds`' min/max index into the full `columns`/`rows` array.
- **Row insert-above/below is only offered when `rowDragEnabled`** (no active sort/search) — same gate row drag-reorder already uses, for the identical reason (manual `order` and an active sort/filter can't both define "row position"). When gated off, the row menu falls back to a single generic "Add row" (appends), rather than a position-specific insert that wouldn't match what's on screen.
- **Sort (A→Z / Z→A) only appears for a single-column target** — `sort` state is inherently one column at a time (`{ columnId, direction }`), so a multi-column selection's context menu omits it rather than sorting by an arbitrary one of the selected columns.
- `insertColumns(beforeColumnId, count)`/`insertRows(beforeRowId, count)` (`useTableStore.ts`) create `count` blank entries at a specific position — `beforeColumnId`/`beforeRowId` of `null` means append at the end. New columns get an auto-generated `"Column N"` name (`nextColumnName()`, skipping any already-taken name) rather than prompting up front, matching Excel's own "insert first, rename after" flow. `insertRows` reassigns `order` across *every* row afterward, the same technique `moveRows` already uses for drag-reorder, so the new rows land at the right position regardless of the current view's sort. `removeColumns`/`setColumnsHidden` (plural, alongside the existing singular `removeColumn`/`setColumnHidden`) exist specifically so a multi-column action pushes one undo-stack snapshot, not N — looping the singular action per id would otherwise make one right-click "Delete columns" require N separate Ctrl+Z presses to undo.

**Hidden columns** (`Column.hidden`, `ColumnHeaderMenu`'s "Hide column") render via `visibility: collapse` on the corresponding `<colgroup>` `<col>` element — **not** `display: none` on the individual `<th>`/`<td>` cells, which was the first approach considered and rejected before writing any code. `display: none` on a table cell removes it from box generation entirely, which changes that row's *effective cell count* for the browser's column-counting algorithm — even hiding the exact same logical column consistently across every row, this creates real ambiguity about whether remaining cells stay aligned to their declared `<col>` position or shift left to fill the gap (a well-known rough edge in the CSS table model). `visibility: collapse` is the purpose-built mechanism for exactly this — hide a column and reclaim its space while leaving every row's cell structure/column-count untouched — and it's what makes hiding a column simply work with zero special-casing anywhere else in the render loop (selection indices, `colSpan` on the virtualizer's padding rows, the Name Box, copy/paste range math — none of them need to know a column is hidden, since `columns` never changes shape, only what's visually rendered does). A hidden column's data is untouched: still written on CSV export, still offered as an "existing column" match target in the CSV import mapping modal, still included if a copy/paste range happens to span it.

**The trailing "+" column header cell and "+ Add row" table row replace the old toolbar buttons**, and exist specifically to keep bootstrapping a brand-new zero-column/zero-row table possible without them. The "+" header cell (`rowSpan={2}`, spanning both header rows) has no corresponding `<td>` in any body row — a column that exists only in the header, with nothing under it, is valid HTML and needs no special-casing elsewhere (nothing iterates "columns including the plus one"). "+ Add row" is a real `<tr>` appended after the virtualizer's own rows and padding rows, always rendered except mid drag-reorder (where "drop here to move to the end" already occupies that same visual slot). Since `columns.length === 0` still shows the plain-text `.empty-state` instead of any table at all (nothing to have a "+" header cell *in* without at least the gutter column), that empty state also needed its own working entry point — `.empty-state-add-column`, a plain button reusing the same `AddColumnPopover` trigger. **This button needed an explicit `e.stopPropagation()` to work at all** — the same document-level-click gotcha documented elsewhere in this file (note/contact cell open-click, the contact-paste `readOnly`-vs-`disabled` bug): without it, the same click that opens `AddColumnPopover` via `setAddColumnAnchor` also bubbles to `.table-view`'s `onClick={closePopovers}`, which clears `addColumnAnchor` right back to `null` in the same batched update, so the popover visibly never opened. Any new button that toggles a popover's anchor state needs this same guard; the existing toolbar buttons already had it, which is why only this new one needed the fix.

**Copy/paste** ([components/Table/TableView.tsx](app/src/components/Table/TableView.tsx), the `copy`/`paste` `useEffect`) hooks the native `copy`/`paste` DOM events on `document` (not the async `navigator.clipboard` API — that needs a permission grant and doesn't fit a keyboard-shortcut-triggered flow as naturally). Both handlers bail out unless focus is inside `.table-scroll` (or nothing in particular is focused), so they never hijack copy/paste in the search box or a popover field. Serialization goes through [utils/tsv.ts](app/src/utils/tsv.ts)'s `buildTsv`/`parseTsv` — both are thin wrappers around Papa.parse/unparse with `delimiter: '\t'`, **not** a hand-rolled `text.split('\n').map(l => l.split('\t'))`. That naive version was a real, shipped bug: Excel/Google Sheets quote a clipboard cell (RFC4180-style, `"..."` with embedded newlines/tabs preserved literally inside the quotes) whenever it contains a tab, newline, or quote character, and a plain `.split('\n')` treats every embedded newline inside a quoted multi-line cell as a row break — pasting a small block containing one multi-line note cell could explode into dozens of extra rows. Papa.parse already implements this quoting correctly (it's the same library CSV import/export already uses), so route any future clipboard-format changes through `utils/tsv.ts` rather than reintroducing manual splitting.

Paste: if the clipboard is exactly one value and the current selection spans more than one cell, that value fills the whole range; otherwise it's placed starting at the selection's anchor, row-major. Rows needed beyond the current table are created on the fly via `addRow()` (whose return value is used immediately — no need to wait for the next render); columns needed beyond the current table are *not* auto-created, just skipped (toasted as "extra columns beyond the table were skipped"). Pasting into a `dropdown` column with a value that isn't already one of its options extends the option list rather than silently dropping the data — mirrors how CSV import treats unknown columns.

**Delete/Backspace clears the selected cell(s) to `''`** via the same `updateCells` batch used by paste's fill mode — wired as a `keydown` listener in `TableView.tsx`, guarded so it only fires when nothing is actively focused in a `<textarea>`/`<input>` (otherwise it'd fight normal text editing) and `withinTableFocus()` passes.

**Undo/redo** ([store/useTableStore.ts](app/src/store/useTableStore.ts)) is a snapshot stack, not per-field diffing. Every mutating action calls a private `snapshot()` first, which pushes `{ columns, rows }` (the state *as of just before* this action) onto `undoStack` and clears `redoStack`, capped at `MAX_HISTORY_DEPTH` (50). This is only cheap because every action already produces fresh `columns`/`rows` arrays rather than mutating in place — snapshotting is just holding a reference, no deep clone needed. `undo()`/`redo()` swap the current state for the top of the relevant stack and push the state they just replaced onto the other stack. Persisting an undo/redo to IndexedDB needs more than `saveRows()` (which only upserts): `syncRowsToDB(previousRows, nextRows)` also deletes rows present in `previousRows` but absent from `nextRows`, so undoing a row-delete restores it and undoing a row-add removes it again. History is per-table and intentionally not persisted — `loadTable`/`unload` both reset both stacks, since undoing into a different table's past state would make no sense. Toolbar buttons + Ctrl/Cmd+Z / Ctrl/Cmd+Shift+Z (or Ctrl+Y) both call the same two store actions.

**The Name Box** (top-left "A1"-style input in the toolbar, [utils/spreadsheet.ts](app/src/utils/spreadsheet.ts) `parseRangeRef`/`formatCellRef`) mirrors Excel's both ways: type a reference like `C13` or `A1:A10000` and Enter jump-selects it (the point being bulk operations — delete, color, clear — on a table with thousands of rows without dragging through all of them), and dragging/shift-clicking a range in the grid updates the box to show it, e.g. `D15:D17`. Submitting sets *both* the cell range (`rangeAnchor`/`rangeFocus`, for copy/paste/color/Delete-key) and the row range (`rowRangeAnchor`/`rowRangeFocus`, for the "Delete selected" bulk-row-delete button) from the same reference, clamped to the table's actual current size — typing a reference beyond the real row/column count just clamps rather than erroring. The reverse direction (selection → box text) is a `useEffect` in `TableView.tsx` comparing `rangeAnchor`/`rangeFocus`: equal means show a single `formatCellRef`, otherwise `anchor:focus` — gated by a `nameBoxFocusedRef` so it doesn't clobber text the user is actively typing into the box.

**The row grid is virtualized** (`TableView.tsx`, `@tanstack/react-virtual`'s `useVirtualizer`) — only rows actually near the scroll viewport are ever mounted, regardless of how many rows the table logically has. This exists because of a real, reproduced crash: importing an actual 14,617-row / 47-column CSV export used to try to mount ~700,000 DOM nodes (every `<td>` × every row) in one React commit, which hung the tab for minutes — indistinguishable from a crash to anyone hitting it. After virtualizing, the same import completes in ~1s and the DOM never holds more than a few dozen `<tr>`s regardless of table size. Row height is always known exactly (`row.height ?? DEFAULT_ROW_HEIGHT`, never derived from rendered content), so `estimateSize` is authoritative and no `measureElement`/`ResizeObserver` dynamic-measurement wiring is needed.

A few things worth knowing if you touch this again:
- **A real `<table>` can't absolutely-position individual `<tr>`s** the way a div-based grid virtualizer normally would — `<tr>`s have to stay in normal table flow for column alignment/layout to work. The standard fix (also what TanStack's own docs show for HTML tables) is two "phantom" padding `<tr>`s — one before, one after the rendered slice — each a single `<td colSpan={columns.length + 1}>` sized to cover the vertical space of every *unmounted* row above/below. `<thead>`'s `position: sticky` doesn't care about any of this either way, since it's positioned relative to the scroll container, not row count.
- **`getItemKey` returns the row's own `id`, not its positional index** — this is what makes sorting/searching safe. The virtualizer caches each item's last-known size *by this key*, so a row's cached height stays correctly attached to *that row* across a re-sort instead of leaking onto whatever row happens to land at the same index afterward.
- **The virtualizer never re-derives a size from `estimateSize` once an index is cached** — changing what `estimateSize` *would* return for a row (e.g. after a resize-drag commits a new `row.height`) does nothing on its own. The row-resize handler explicitly calls `rowVirtualizer.resizeItem(index, liveHeight)` on every drag tick (not just on mouseup) specifically so rows below the one being resized visibly shift in real time instead of jumping once at the end.
- **`rowRefs`, the old `Map<rowId, HTMLTableRowElement>` populated via each `<tr ref={...}>`, is gone.** It only worked because every row was always mounted; a row scrolled out of view now simply isn't in the DOM, so nothing keyed off "read the ref" can work anymore. Every "jump to this row" interaction (Calendar's `onJumpToRow`, the Name Box's cell-reference jump, `handleAddRow` scrolling to a freshly-created row) now goes through `scrollToRowIndex`/`scrollToRowId`, which call `rowVirtualizer.scrollToIndex()` — this works correctly even for a row that isn't currently rendered, since the virtualizer tracks every item's computed offset regardless of mount state. `handleAddRow` in particular needs the *id*-based lookup (`scrollToRowId`, reading a `filteredSortedRowsRef` kept in sync every render) rather than an index, since a search/sort can place a newly-added row anywhere in `filteredSortedRows` or filter it out of view entirely — the old "just scroll to the ref" code silently no-opped in that case too, so this preserves the same graceful-failure behavior, just via a different mechanism.
- Large CSV imports also show an interim "Importing X MB…" toast (`handleFileChange`, gated on `file.size > 1_000_000` so it doesn't flash uselessly for small files) — the parse + row-object-building step itself still takes on the order of a second for a file this size, which is fine, but was enough to read as "did my click even register?" with zero feedback.

**The status dropdown is styled as a rounded pill/badge** (`.cell-dropdown select` in `App.css`) via `appearance: none` plus a hand-drawn chevron background-image, not the native `<select>` chrome — still a real `<select>`, just reskinned, so no custom dropdown component was needed. Uncolored (no `optionColors` entry) renders transparent/plain, matching an unformatted Excel cell; once a color is set it's applied as an inline `background-color` (see `DataCell.tsx`), which wins over the CSS default.

When adding a new column type, follow the existing pattern: add it to `ColumnType`, handle it in `DataCell.tsx` (decide whether it needs the display/edit-modal split or can stay a native always-interactive control), and if it needs cross-cutting behavior (like the next-action date), add a helper in `utils/row.ts` rather than querying `columns`/`rows` ad hoc in components.

**The `link` column type** (websites, LinkedIn, etc.) edits exactly like `text`/`phone`/`company` — single click, live `<input type="url">` — but its non-editable preview is two independent click targets side by side in a `.cell-link-inner` div: the text (click to edit, same as every other type) and a 🔗 `<a>` (click to open in a new tab, `stopPropagation` on both `onMouseDown`/`onClick` so it doesn't also trigger cell-select). The stored value is left exactly as typed (`"google.com"`, no protocol) — `ensureProtocol()` ([utils/link.ts](app/src/utils/link.ts)) only adds `https://` at the point of forming the actual `href`, so the raw cell value and CSV export aren't silently rewritten into something the user didn't type.

**A real, shipped bug worth remembering when naming anything inside a cell**: the `link` cell's inner wrapper div was first named `cell-link` — which collided with the *cell's own* class, since `DataCell.tsx` always applies `cell-${column.type}` to the `<td>` itself, and `column.type === 'link'` produces exactly that same string. The result: `.cell-link { display: flex; ... }` (meant only for the inner wrapper) also landed directly on the `<td>` via the collision — the exact "`display: flex` on a `<td>` silently breaks `table-layout: fixed`" trap already documented for the Calls tab elsewhere in this file, except here it broke **row height**, not just column width: a link cell's `<td>` measured visibly *shorter* than its own `<tr>` (confirmed directly — `27.375px` rendered vs. `34px` row height), and since the row virtualizer positions every row from `estimateSize()`'s fixed heights (never re-measured from actual rendered content), every row below the first one with a populated link cell drifted further out of alignment with the rest of the table — reported as "Линий сбились" (the lines got mixed up), reproduced and confirmed via a real screenshot before the fix. Fixed by renaming the inner div to `.cell-link-inner` (never reuse `cell-${column.type}`'s own name for anything nested inside that cell) plus `height: 100%; overflow: hidden` on it as a second guard against the same class of bug recurring. If a future cell type's preview needs an inner wrapper element, give it a name that can't collide with `cell-${type}`.

**In-app search** ([components/Table/TableView.tsx](app/src/components/Table/TableView.tsx)) does two things beyond the plain substring filter (`filteredSortedRows`, described above): Ctrl/Cmd+F is intercepted (`e.preventDefault()`) to focus/select the search box's own `<input>` instead of triggering the browser's native find-in-page — which mostly failed anyway against this virtualized table, since native find can only match text actually mounted in the DOM, and almost all rows in a real-sized table aren't at any given moment. And every matching cell highlights *where* the match is: `highlightMatches()` ([utils/highlight.tsx](app/src/utils/highlight.tsx)) wraps each case-insensitive occurrence in a `<mark className="cell-highlight">`, called only on the cells of rows the filter already matched (never run over the whole table). `DataCell` takes this as a `highlightQuery?: string` prop — **and it had to be added to the memo comparator**, unlike `onSelect`/`onExtend`/`onOpenEditor`: those callbacks are excluded from comparison because they're fresh-but-equivalent closures every render, but `highlightQuery`'s *value* actually changes what renders (which substring, if any, gets wrapped), so skipping re-render on it would leave stale highlights on screen after the search box changes. Only applies to the plain-preview render paths (text/phone/company/link/note-summary/contact-summary) — an `editable` cell renders a live `<input>`, which can't show rich `<mark>` formatting inside its value, so the currently-selected cell's own highlight (if any) simply doesn't show until you click elsewhere.

**Every `window.confirm()` in the app was replaced with a custom in-app dialog** ([store/useConfirmStore.ts](app/src/store/useConfirmStore.ts), [components/ConfirmDialog.tsx](app/src/components/ConfirmDialog.tsx), mounted once in `App.tsx`), on explicit request — the native browser dialog didn't match the app's own design. `confirmDialog(message | options)` returns a `Promise<boolean>`, so every call site that used to be a synchronous `if (window.confirm(...))` became `if (await confirmDialog(...))`, with the enclosing handler turned `async`. `ConfirmDialog` itself just renders whatever's in the store's `request` (or nothing) using the same `.modal`/`.modal-backdrop` chrome as `CsvImportMapping`, so every centered dialog in the app looks consistent.

**Deleting a whole table gets one extra confirmation step beyond every other delete in the app** — `confirmDeleteTable()` ([utils/confirmDeleteTable.ts](app/src/utils/confirmDeleteTable.ts)) chains two `confirmDialog()` calls, the second more strongly worded ("Are you sure? This will permanently delete... This cannot be undone.") — on explicit request, since this is the one action in the app with no undo path at all (undo/redo history is per-table and reset on load, so there's nothing to Ctrl+Z back into even immediately after). Shared by `WorkspaceView`'s Delete button and `SheetTabs`' right-click "Delete table" so both paths ask the same way rather than duplicating the two-step prose.

**SheetTabs** ([components/SheetTabs.tsx](app/src/components/SheetTabs.tsx)) — Excel-style tabs along the bottom of the window (mounted in `App.tsx`, sibling to `<main>`, always visible once a table is open regardless of the Table/Calendar/Calls sub-tab, matching how Excel's own sheet tabs aren't scoped to "whatever you're currently looking at"). Click switches `useWorkspaceStore`'s active table without a round trip through the Workspace screen; right-click opens a `ContextMenu` with **Rename**, **New table**, **Duplicate table**, and **Delete table** (the last through `confirmDeleteTable()` above) — one menu for everything, on explicit request. An earlier version put rename on double-click instead, alongside single-click-to-switch; reversed after a real report that the two were easy to trigger by mistake for each other — right-click is unambiguous where a click-count distinction wasn't. No new data relationship between tables is introduced by any of this — it's purely a faster path to state `useWorkspaceStore` already had (`tables`, `setActiveTable`), and `WorkspaceView`'s own cards keep working exactly as before.

- `duplicateTable(id)` (`useWorkspaceStore.ts`) clones a table's columns (fresh ids, remapped into a `columnIdMap`) and every row (fresh ids, `cells`/`colors` keys remapped through that same map) into a brand-new `TableMeta`. Two real bugs surfaced while building and testing this, both worth remembering for any future code that touches a table right after creating/duplicating it:
  1. **It read the source table's columns from `get().tables`' cached `TableMeta` instead of re-reading fresh from IndexedDB (`getTable(id)`).** This is exactly the class of bug `loadTable`'s own "always re-fetch, never trust the cached copy" rule (documented earlier in this file) exists to prevent: `useWorkspaceStore.tables[i].columns` is a snapshot from whenever the workspace list last loaded, and is never updated when `useTableStore` edits columns — only the IndexedDB record is. Reproduced directly: add a column to a table through the normal UI, immediately right-click → Duplicate, and the copy came out with **zero columns**, because `get().tables` still held that table's columns as they were before the add. Fixed by fetching fresh via `getTable(id)` instead of `get().tables.find(...)`.
  2. **`saveTable`/`saveRows` were fire-and-forget (`void saveX(...)`), but the caller switches to viewing the new table immediately after `duplicateTable()` resolves**, and `loadTable()` does a one-shot IndexedDB read with no retry — so the new table could render as empty (or worse, stay empty indefinitely) if those writes hadn't actually landed by the time the read happened. Fixed by `await`-ing both before returning the new table's id, unlike the fire-and-forget pattern every other write in this store otherwise uses.

## Login gate (`server/src/auth.ts`, `app/src/store/useAuthStore.ts`)

Added once the app moved from `localhost` to a real public domain (`app.serteo.lt`) — anyone with the URL could otherwise open it. One shared account (this is a single-operator tool, not multi-tenant, so there's no sign-up/user table, just `AUTH_USERNAME`/`AUTH_PASSWORD` env vars on the `server/` deployment).

**Enforced server-side, not just as a frontend gate.** `requireAuth` middleware wraps every route in `index.ts` *except* `/health` and `/api/auth/login` — a visitor who never loads the React app at all and hits `api.serteo.lt`'s routes directly is blocked there too. A frontend-only check (hide the UI until a client-side password match) would have been trivially bypassable by reading the JS bundle, and wouldn't have stopped direct requests to the Zadarma/OpenAI/ElevenLabs-backed routes anyway.

**Sessions are a signed, stateless token, not a real JWT library or a server-side session store** (`issueToken`/`verifyToken` in `auth.ts`) — `base64url(username.expiry.HMAC-SHA256(username.expiry))`, 30-day expiry. No dependency added for this: the payload is two fields, and it mirrors the hand-rolled HMAC signing this codebase already does for Zadarma. Every credential/signature comparison uses `crypto.timingSafeEqual`, not `===` — a plain string comparison leaks how many leading characters matched through response timing, letting an attacker recover a password/token byte by byte.

**Password recovery is a second, independent password (`AUTH_RECOVERY_PASSWORD`), not a security question or email reset** — on explicit request, reasoning that a security question ("what color is your cat") is guessable by anyone who knows the account holder personally, where a second secret they choose isn't. `checkCredentials()` accepts either password for the one account and tells the caller which one matched; logging in via recovery still issues a completely normal token (there's no separate "you're now in reset mode" state) — the frontend (`App.tsx`) just shows a dismissible banner asking the user to go update `AUTH_PASSWORD`. **There is deliberately no in-app "change password" flow that writes anywhere**: `server/` runs on Render's free tier, which has no persistent disk — anything the running process wrote to its own filesystem would vanish on the next deploy or restart, silently reverting the password change and potentially locking the user out with no warning. Changing either password is a manual edit in Render's environment-variables UI, the same place every other secret in this app already lives (`ZADARMA_API_KEY`, `OPENAI_API_KEY`, etc.) — consistent with how this project already handles secret rotation, not a new pattern invented for this feature. (This same ephemeral-filesystem fact is why [server/src/dataDir.ts](server/src/dataDir.ts) exists — see the table-data persistence section above.)

**Token storage/attachment is split into its own module** ([utils/authToken.ts](app/src/utils/authToken.ts)) specifically to avoid a circular import: `useAuthStore.ts` needs `localApiRequest` (to call the login endpoint), and `localApi.ts` needs to read the current token (to attach `Authorization: Bearer <token>` to every request) and react to a 401 by logging out — if `localApi.ts` imported the store directly, that's `useAuthStore → localApi → useAuthStore`. `authToken.ts` sits below both: it owns the `localStorage` key and a single subscriber slot (`setUnauthorizedHandler`, called once by `useAuthStore` at module load) that `localApiRequest` calls into on any 401, so a stale/expired token gets cleared from both `localStorage` and the store's in-memory state together — without the callback, `localApiRequest` clearing storage alone would leave the UI thinking it's still logged in until a full page reload.

**Local dev can skip the gate entirely, on explicit request** ("for localhost:5173 you can delete password... but in main serteo.lt keep it") — two independent, deliberately-can't-leak-to-prod bypasses, one per side of the gate: `App.tsx`'s `if (!token && !import.meta.env.DEV)` skips rendering `LoginScreen` at all, and `requireAuth` (`auth.ts`) returns `next()` immediately when `process.env.AUTH_DISABLED === 'true'`. Both are safe by construction rather than by discipline: `import.meta.env.DEV` is a Vite compile-time constant — `false` in every `vite build` output (what actually ships to `app.serteo.lt`), regardless of any runtime env var, so there's no config flag on the frontend side that could accidentally re-enable this in production. `AUTH_DISABLED` is a real env var, but it only ever gets set in `server/.env` (gitignored, local-only) — never in Render's dashboard — the same "exists only in the file that never leaves your machine" pattern this app already uses for `HOST=0.0.0.0` (index.ts) needing to be a Render-only override rather than a local default. With both skipped, a local run needs neither a login screen nor a bearer token to reach any route, including the Zadarma/OpenAI/ElevenLabs ones.

## Zadarma Calls tab (`server/` + `app/src/components/Calls/`)

**Why this is the only feature in the app with a backend.** Zadarma's API signs every request with HMAC-SHA1 using a secret key, computed however the caller wants — but that secret must never appear in code that ships to a browser, since anyone with dev tools open could read it out of the bundle and make authenticated calls as the account owner (pull recordings, run up transcription usage, etc.). `server/` is a small local Express/TypeScript proxy that holds the secret in a git-ignored `.env` and signs requests on the app's behalf; the browser only ever talks to `http://localhost:4000`, never to `api.zadarma.com` directly. It binds to `127.0.0.1` explicitly (never the default all-interfaces bind) so the secret is never reachable from the local network, and its CORS policy allowlists only the known Vite dev origins (`5173`/`5174`), not `*`.

**The signing algorithm** ([server/src/zadarma.ts](server/src/zadarma.ts)), ported from Zadarma's official PHP reference client: sort params by key, URL-encode them PHP-`http_build_query`-style, build `signatureString = method + paramsStr + md5(paramsStr)`, HMAC-SHA1 that with the secret, then **base64-encode the HMAC's hex-string representation — not its raw bytes.** This second part is the one gotcha that actually cost real debugging time: PHP's `hash_hmac($algo, $data, $secret)` defaults to `$raw_output = false`, meaning it returns a lowercase hex *string*, and it's that hex string's ASCII bytes that get base64-encoded (`base64_encode(hash_hmac(...))`). Going straight from the HMAC's raw 20-byte digest to base64 (skipping the hex round-trip — the obvious thing to do, and what this code did on the first pass) produces a completely different, wrong signature, and Zadarma's API responds to *any* signature mismatch with a generic `{"status":"error","message":"Not authorized"}` — indistinguishable from an actually-invalid key, an IP restriction, or a pending email-confirmation step on a freshly-created key. All of those were ruled out one at a time (independently re-deriving the empty-params signature via `openssl dgst -sha1 -hmac` from the command line to confirm the *math* was right, testing the simplest possible endpoint with zero params to minimize surface area, trying key/secret swapped) before the actual bug — the missing hex round-trip — was found by comparing against a known-working Python reference snippet line by line. If a future endpoint's signature ever fails the same way, re-check this exact detail first before suspecting param encoding or the account itself.

The second, smaller trap in the same file: params must be filtered by `!== undefined`, never by truthiness — `skip: 0` and `alternatives: 0` are meaningful values a naive falsy-filter would silently drop before signing. Each typed wrapper function builds its own params object with conditional spreads (`...(sip !== undefined ? { sip } : {})`) rather than routing through a generic "strip empties" helper, so there's no shared code that could get this wrong for every call at once.

**`getStatistics` calls `/v1/statistics/pbx/`, NOT the plain `/v1/statistics/` — this one detail cost the most debugging time of the whole feature, and is worth understanding precisely if the Calls tab ever breaks again.** Zadarma has *two* different call-listing endpoints, and they report call identifiers in completely different, incompatible formats:

| Endpoint | Example `call_id`/`id` |
|---|---|
| `GET /v1/statistics/` (plain) | `"6a8146e0fd8fc1013a966bd9"` |
| `GET /v1/statistics/pbx/` (PBX) | `"1786857078.38121"` |

Only the **PBX** endpoint's `call_id` is accepted by `GET /v1/pbx/record/request/` and, downstream of that, by transcription. Passing the plain endpoint's `id` doesn't error loudly — Zadarma just replies with its generic `{"status":"error","message":"Requested file not found"}`, identical to what you'd see if a call genuinely had no recording. This was mistaken for an *account-configuration* problem for a long time: recording was confirmed disabled, then enabled (with cloud storage as the destination, per a real support exchange), a fresh test call was made afterward, and it *still* failed the same way — because the code was built against the plain endpoint's `id` the entire time, and no amount of correct Zadarma-side configuration could have fixed a client-side field mismatch. The bug was only found by directly calling `/v1/statistics/pbx/` for the same call and diffing its response shape against what `/v1/statistics/` returned for the same time window — the `is_recorded` field on the PBX response (`"true"` for that exact call) was the smoking gun that recording had, in fact, been working the whole time. **If "Requested file not found" ever resurfaces, check which statistics endpoint the `call_id` in hand came from before assuming anything about the Zadarma account.**

This is also why `getStatistics`'s `CallRecord` shape (`call_id`, `sip`, `callstart`, `clid`, `destination`, `disposition`, `seconds`, `is_recorded`) looks different from a typical Zadarma CDR — it's deliberately the PBX endpoint's fields, not the richer plain-statistics ones (no `cost`/`billcost`/`currency`/`from`; `clid` is a caller-id label like `"Extension 100"`, not a raw phone number). The `is_recorded` boolean (Zadarma sends it as the *string* `"true"`/`"false"`, normalized to a real boolean in `getStatistics`) is used to hide the Recording/Transcribe actions entirely for calls that were never recorded, rather than letting the user discover that by hitting a failed request.

**Two Zadarma wrappers remain** in [server/src/zadarma.ts](server/src/zadarma.ts) — `getStatistics`/`requestRecording`, mapping to `GET /v1/statistics/pbx/` and `GET /v1/pbx/record/request/`. Zadarma's own speech recognition (`PUT`/`GET /v1/speech_recognition/`) was removed entirely and replaced with dedicated transcription/summary providers (see below) — cheaper, and simpler since neither is an async job. [server/src/index.ts](server/src/index.ts) exposes `GET /api/calls`, `GET /api/calls/:callId/recording`, `POST /api/calls/:callId/transcribe`, each wrapped in a small `asyncHandler` (Express 4 doesn't auto-catch async rejections) and funneled through one error middleware mapping a `ZadarmaApiError`/`TranscriptionError`/network failure to `502`, validation failures to `400`, anything unexpected to `500` — one `{ error: string }` shape everywhere, so the frontend has exactly one parsing path ([app/src/utils/callsApi.ts](app/src/utils/callsApi.ts)'s `request()` helper).

**Transcription goes through ElevenLabs Scribe, not OpenAI — switched on explicit request after whisper-1's Lithuanian accuracy produced a real, embarrassing error (the model mis-gendered the caller's own name mid-transcript).** [server/src/elevenlabs.ts](server/src/elevenlabs.ts)'s `transcribeFromUrl()` downloads the audio from the Zadarma recording link `requestRecording` returns, then POSTs it to `https://api.elevenlabs.io/v1/speech-to-text` (`model_id: 'scribe_v2'`, `language_code: 'lt'`) as multipart form data. Published FLEURS-benchmark WER for Lithuanian backs up the switch decisively — whisper-1/Large-v3 around 30.5% vs. Scribe's ~7.3% — and it's not even a cost tradeoff: Scribe is $0.22/hr (≈$0.0037/min) against whisper-1's $0.006/min, so this is strictly better on both accuracy and price. Verified directly against a real ~4-minute production call: clean, grammatically correct Lithuanian output, correct gender agreement throughout.

**Two gotchas specific to this integration, both easy to get wrong by pattern-matching the *other* two API integrations already in this file:**
1. **Auth header**: ElevenLabs uses its own `xi-api-key` header, not `Authorization: Bearer <key>` (which is what both the OpenAI calls in `openai.ts` use) and not Zadarma's HMAC-signed-params scheme (`zadarma.ts`). Three different auth schemes for three different providers in this one small server — don't assume any of them generalizes to the next one added.
2. **API key permissions**: an ElevenLabs key can be scoped to a subset of capabilities, and Speech-to-Text is not necessarily included by default — the first live test against a real key failed with a clean `"missing the permission speech_to_text"` error, fixed entirely on the ElevenLabs dashboard (Settings → API Keys → edit permissions) with no code change. If transcription ever starts failing with a permissions-flavored error after rotating the key, check this before suspecting the request code.

The filename-extension gotcha carries over unchanged from the old OpenAI integration: the API infers audio format from the *uploaded filename's extension*, not Content-Type, and Zadarma always serves `.ogg` regardless of what (if anything) the recording URL's path suggests — `extensionFromUrl()` in `elevenlabs.ts` handles this the same way the old `openai.ts` version did. Because this endpoint blocks until ElevenLabs finishes (unlike Zadarma's own async-job speech recognition), there's exactly one route — no separate start/poll pair, and correspondingly **no polling logic anywhere in the frontend either** (an earlier version had a component-owned `setInterval` for this; it was deleted entirely once the backend stopped being async).

`server/.env`'s `OPENAI_API_KEY` is still required — it now only powers the two `openai.ts` features below (contact-paste cleanup, call summary), not transcription. `ELEVENLABS_API_KEY` is the one transcription actually needs.

**A finished transcript can be collapsed** (`CallRow.tsx`'s `showTranscript` state, defaults to `true` so it's visible the moment it finishes) — added because a 20-minute call produces a genuinely long block of text per row, and once read there was no way to shrink it back down short of scrolling past it forever. Two identical toggle buttons control the same state (one in the row's action column, one inside the expanded transcript block itself) purely for convenience — collapsing from either spot is equivalent.

**AI call summary** (`🤖 Summary`/`🤖 Re-summarize` button, `summarizeCall` in `server/src/openai.ts`, `POST /api/calls/:callId/summarize`) — a second, separate AI step layered on top of an already-finished transcript, not a replacement for it: 3-5 sentences (what was discussed, the prospect's interest/reaction, agreed next steps or objections) via a cheap `gpt-4o-mini` chat completion, same model/cost tier as the contact-paste cleanup above. Output is **in Lithuanian, matching the transcript** — an earlier version summarized in English to match this app's own UI language (reasoning: a short English gloss reads faster than the full Lithuanian transcript), reversed on explicit request since the account is worked in Lithuanian day-to-day and a summary in a different language than the call itself was a worse fit than that "faster skim" reasoning assumed. The button only ever appears once `transcript.text` already exists (`CallRow.tsx`) — summarizing never triggers transcription on its own, since that's the one step in this whole feature that actually costs real per-minute money and should stay an explicit, separate click. The summary rides inside the *same* collapsible block as the transcript (a highlighted callout above the raw text, `.calls-summary-block`) rather than getting its own independent show/hide — asked for explicitly as "one thing I can open/close," not two. Cached the same way transcripts are: `TranscriptionResult` (`utils/callsApi.ts`) gained an optional `summary` field, and `saveTranscription`/`hydrateTranscription` persist and restore it alongside `text` in the same IndexedDB record, so it survives reopening the tab exactly like the transcript does.

**Frontend**: [store/useCallsStore.ts](app/src/store/useCallsStore.ts) follows this codebase's usual `ready: boolean` + async-action convention (mirrors `useTableStore.loadTable`), but is the first store here to hold real `try/catch` error state — no store calls `showToast` itself anywhere in this app, and this one doesn't either; `CallsView`'s `useEffect` watching `error` is what toasts, keeping every store consistent on "components own side effects, stores own data." A finished transcription (and, once generated, its summary) is cached in IndexedDB ([db/db.ts](app/src/db/db.ts), `DB_VERSION` 4, `transcriptions` store keyed by `callId`) so reopening the tab or switching away and back shows it instantly via `hydrateTranscription` (an IDB-only read, no network) instead of re-paying to re-transcribe/re-summarize a call already done.

**`display: flex` directly on a `<td>` silently breaks `table-layout: fixed`'s column widths** — cost real debugging time chasing what looked like a data problem before it turned out to be pure CSS. `.calls-table` has no virtualization or complex selection systems to protect (unlike `table.sheet`), but it still needed `table-layout: fixed` + explicit `nth-child` percentage widths added, for the same reason as everywhere else fixed layout shows up in this app: without it, a transcript row appearing/disappearing (or the audio player showing up under "▶ Recording") let the browser's auto-layout algorithm re-measure and shift *every other* column's width based on whatever happened to be visible, which read as the whole table "jumping" on every click — reported as call rows looking "jumbled/mixed up," which turned out to describe this plus a second, unrelated issue below, not literally wrong data (nothing was ever actually misaligned between a row's cells and its own call). Adding `table-layout: fixed` alone wasn't enough, though: the Number and Actions columns (the two whose classes — `.calls-destination`, `.calls-row-actions` — set `display: flex`) kept ignoring their assigned widths and sizing to content instead (measured ~90px against a declared 24%/31%), while the four plain `<td>` columns matched their percentages exactly. Root cause: putting `display: flex` straight on a table cell makes browsers size that cell by its flex content, bypassing the fixed-layout column grid entirely — a real, if obscure, CSS interaction. Fixed by moving both classes off the `<td>` and onto a plain child `<div>` instead, so the `<td>` itself stays an ordinary table-cell (fixed-layout width applies) while the inner div still lays out its own children with flexbox exactly as before. The *other* half of the "jumbled" complaint was simpler: recorded calls' Actions column stacked "▶ Recording" and "📝 Transcribe" vertically (`flex-direction: column`), making a recorded call's row roughly twice as tall as an unrecorded one's single-line "Not recorded" — repeated down a long list, that height mismatch alone was enough to make the table feel like it had no consistent row rhythm. Changed to `flex-direction: row` (wrapping only when there's genuinely more to show, like the audio player) so the *resting* height stays close to one line regardless of `is_recorded`.

**Transcription is manual, one call at a time, on purpose** — every call's `CallRow` (when `is_recorded`) just shows a "📝 Transcribe" button. An earlier version added a `transcriptionMode` picker (Manual / Without recognition / Transcribe-all-with-a-cost-estimate) plus a `transcribeAll` batch action in the store, built from a misreading of a question that was actually about a *Zadarma dashboard* setting, not a request for in-app batch tooling — removed again once that was clarified, since per-call manual control via the existing button was already exactly what was wanted. If batch transcription is ever actually requested, `useCallsStore`'s `transcribe` action (single-shot, already there) is the right thing to loop over with a small fixed-concurrency worker pool — don't reintroduce a full mode-picker UI for it unless multiple trigger *styles* are actually needed, not just "do many at once."

`getStatistics` sorts results newest-call-first before returning (`callstart` is a sortable `YYYY-MM-DD HH:MM:SS` string) — Zadarma's `/v1/statistics/pbx/` returns them oldest-first, and "what happened most recently" is the useful order for a tab you check in on throughout the day.

`.calls-table` in `App.css` is a deliberately separate, simple ruleset — **not** `table.sheet`, which carries ~120 lines of spreadsheet-specific machinery (sticky headers, resize-drag hooks, `cell-row-bg`-scoped zebra/hover selectors) this read-only list has no markup for and would gain nothing from. It also has no `nth-child`-based zebra striping: a call's transcript renders as an extra sibling `<tr>` only when one exists, so row-count-per-call is irregular and position-based striping would visibly misalign once some calls have transcripts and others don't.

**Zadarma's `/v1/statistics/pbx/` sends `destination` as a bare, unquoted JSON number, not a string** — despite it being phone-number-like data and `CallRecord` typing it `string`. This is silent at the type-checker level (TypeScript trusts the declared type, doesn't verify it against what actually comes back over the wire) and only surfaces at runtime the first time something calls a string method on it — `phoneMatchKey()`'s `.replace()` (see below) threw `value.replace is not a function` the first time a real destination number flowed through it. Fixed in two places, deliberately redundant: `getStatistics` coerces `destination: String(c.destination)` server-side so the type is actually true by the time it reaches the frontend, *and* `normalizePhoneDigits()`/`phoneMatchKey()` accept `string | number` and coerce internally regardless, so a future field with the same quirk doesn't reintroduce the same crash. If a new Zadarma field ever looks numeric, don't trust the docs or the TypeScript interface — check what actually comes back.

**Clicking a contact's phone number sends it straight into the Zadarma softphone widget's own input** ([utils/softphoneBridge.ts](app/src/utils/softphoneBridge.ts), wired into `CellHoverEditor.tsx`'s phone field — the 📋 copy button next to it is unchanged, this is a *second*, independent action on the number text itself) — on explicit request, so the only manual step left is pressing the widget's own Call button, instead of copy-then-manually-paste. There's no documented "dial this number" JS API for the widget (same gap the 📞 click-to-call buttons below work around a different way), so this drives the widget's actual rendered DOM directly: `document.getElementById('zdrm-webphone-phonenumber-input')`, confirmed live (via Playwright, inspecting the real widget) to be a plain, undisguised `<input>` — not behind a shadow root or iframe. **A bare `input.value = x` does nothing** — the widget tracks the field reactively and only notices a change through the events it's actually listening for, so the fix is going through the *native* `HTMLInputElement` value setter (bypassing whatever the widget's own framework may have overridden `value` to do) and then dispatching a real `input` event; confirmed the injected value survives (isn't silently reset) at least 1.5s later, i.e. it's genuinely accepted, not just cosmetically displayed for one paint. Undocumented and reverse-engineered, with no supported fallback if Zadarma ever renames the input or changes its event wiring beyond what's already there: `insertIntoSoftphone()` returns `false` when the element isn't found at all (widget disabled, still loading, or failed), and the caller falls back to the existing copy-to-clipboard behavior rather than a dead click.

**Click-to-call** (`requestCallback` in `zadarma.ts`, `POST /api/callback`, wraps `GET /v1/request/callback/`) dials your own number first (`ZADARMA_CALLER_NUMBER` in `server/.env` — a real phone number like `+37066653965`, not a SIP extension, since calls are actually answered on the Zadarma mobile app on that number, not a desk/softphone) and connects you to the destination once you pick up — no public URL needed, it's a plain outbound signed request like every other wrapper here. Wired into [components/Table/CellHoverEditor.tsx](app/src/components/Table/CellHoverEditor.tsx)'s contact list as a "📞" button per entry, shown only when `utils/contacts.ts`'s `extractPhoneNumber()` finds something phone-shaped in that contact's freeform text (a regex requiring 7+ digits, specifically so it doesn't fire on a short filler value). Because contacts collapsed down to a single free-text field a few turns before this (see the `contact`-type section above), there's no dedicated phone field to hang a "Call" button off of directly — extraction is a pragmatic fallback given the freeform-text architecture, not the ideal design in isolation. This didn't get a live end-to-end test the way everything else in this feature did: unlike statistics/recording/transcription, calling this endpoint has a real-world side effect (it rings an actual phone), so it was verified structurally (route validation, missing-param handling) but not by placing an actual call.

**A multi-line paste into the Contacts AI-cleanup field was leaking into the surrounding table cells — root cause was `disabled`, not the paste logic itself.** The contact `<input>` set `disabled={parsingContact}` while the AI call was in flight, intending to block editing during that window — but disabling a *focused* form control forces an immediate browser blur, moving `document.activeElement` to `document.body`. `TableView.tsx`'s own paste handler bails out via `withinTableFocus()` (`active === document.body || tableScrollRef.current?.contains(active)`) — and `document.body` satisfies that check directly, so the instant the input got disabled, the table's own handler started treating the *same* clipboard paste as fair game, running its multi-cell TSV-paste logic starting from wherever `rangeFocus` last pointed (the Contacts cell that had just been clicked to open the editor). Two independent fixes, both applied: the input uses `readOnly` instead of `disabled` (blocks typing without ever touching focus), and the paste handler now calls `e.stopPropagation()` in addition to `e.preventDefault()` — portaled content is a genuine DOM descendant of `document.body`, so this native event bubbles all the way to `document` regardless of React's portal semantics (React's synthetic-event component-tree-bubbling quirk, documented elsewhere in this file, only applies to *other React handlers*, not a raw `document.addEventListener` listener). **The general lesson**: disabling a focused input is never side-effect-free — if code elsewhere depends on focus state (a global "is focus inside X" check, in this case), reach for `readOnly` instead whenever the goal is "block editing," not "remove from the tab order."

**AI contact-paste cleanup** (`parseContactText` in `server/src/openai.ts`, `POST /api/contacts/parse`, a `gpt-4o-mini` chat completion) exists because contacts are commonly copy-pasted in from lead databases (Apollo, LinkedIn) as a messy multi-line blob — name, title, company, and several lines that may or may not be real phone numbers, including placeholder/masked values like a bare `"+1"`. `CellHoverEditor`'s contact `<input>` has an `onPaste` handler that only intercepts *multi-line* pastes (`pasted.includes('\n')`) — a normal single-line paste or plain typing is completely untouched, so the common case never spends anything on an API call. The system prompt explicitly tells the model to extract name/title/company/email/one real phone number and drop placeholder values; verified against the user's actual real-world Apollo export during implementation, correctly dropping two separate junk `"+1"` lines while keeping the one real `+370` number. The AI's output lands back in the same input field — it doesn't auto-submit — so the user still reviews/edits before "+ Add contact" actually saves anything.

**Linking a call to its CRM row** (`CallsView.tsx`'s `phoneToRow`, built with `utils/phoneMatch.ts`) matches a call's `otherParty` (**not** `destination` — see below) against every `phone`-type column's cell values across the *active* table, using a last-7-digits suffix match (`phoneMatchKey()`) rather than exact-string comparison — real numbers show up with or without a country code and in wildly different formatting (`"+370 61 818301"` vs `"37061818301"` vs `"861818301"`), and 7 trailing digits is specific enough to avoid false positives from short extension-like values while being tolerant of all of that. Built once per render as a `Map<matchKey, {rowId, label}>` (`O(rows)`), then a plain map lookup per call (`O(calls)`) — deliberately not a nested loop, which would be `O(rows × calls)` for no benefit. `onJumpToRow` is threaded down from `App.tsx` exactly the same way Calendar already receives it (switches to the Table tab, flash-highlights the row) — this tab reuses that existing cross-tab-navigation plumbing rather than inventing a second one.

**`CallRecord.otherParty` exists because `destination` alone is only meaningful for outbound calls** — for an *inbound* call, `destination` is your own short internal extension (the line being rung, e.g. `"100"`), not the caller. The caller's real number is embedded in `clid` instead (Zadarma formats it like a SIP header: `"+37061200219" <+37061200219>`), so matching/displaying "the other party" needs to pick the right field per call, computed once server-side in `extractOtherParty()` (`zadarma.ts`) rather than duplicated in every consumer: if `destination`'s digit count is short (≤5, i.e. extension-shaped), pull the number out of `clid` instead; otherwise `destination` already is the external party. Two real bugs came out of getting this extraction right: (1) the initial version stripped *all* non-digit characters from the whole `clid` string — but `clid`'s format repeats the same number twice (quoted display-name part + bracketed URI part), so a blanket strip concatenated both occurrences into one doubled, garbage digit string (`"37061200219"` twice back-to-back). Fixed by matching just the *first* phone-shaped digit run (`/\+?\d[\d\s().-]{5,}\d/`) before stripping non-digits from that specific match, not the whole string. (2) `destination` itself comes back from Zadarma as a bare, unquoted JSON number (not a string, despite being phone-number-shaped data) — same class of type-lies-at-runtime issue documented above for the plain `destination` field, coerced the same way (`String(...)`) before the digit-count check runs.

`.calls-copy-btn` (the 📋 next to a call's number, and on a finished transcript) originally shipped icon-only with no border/background — technically present and functional, but easy to miss entirely against the row (reported as "I couldn't find it"). Given a visible label (`📋 Copy`) and a real border/background so it reads as an actual button rather than decorative text.

**A hard, real limit worth knowing about**: Zadarma caps `/v1/statistics/` (and by extension `/pbx/`) at **10 requests/minute** (100/minute for other endpoints) — hit not just during rapid manual re-testing but in normal use too (adjusting the date range and re-clicking "Load calls" a few times), surfaced as Zadarma's own `"You exceeded the rate limit by User Limits"` error. Three mitigations, all in `CallsView.tsx`/`useCallsStore.ts`: the date range **defaults to today only** (`defaultDateInput(0)` for both start and end, not a 7-day window) since checking in on today's activity is the actual common case and it's one less thing to reset before every load; the "Load calls" button enters a 7-second cooldown (`Wait Ns…`, disabled) after every click — comfortably under 9 requests/minute for normal use without being annoying for a tab that's fundamentally "load once, work with it"; and `fetchCalls`'s catch block pattern-matches Zadarma's raw rate-limit message and reframes it as the transient, waitable thing it actually is, rather than surfacing Zadarma's exact wording (which reads more like a real failure than "you're going a bit too fast"). Deliberately **no auto-refresh/polling** for newly-arrived calls — periodically re-hitting a 10-req/min-capped endpoint in the background would reintroduce the exact problem these mitigations exist to prevent; after finishing a call, click "Load calls" again (respecting the cooldown) the same as any other refresh.

**Statistics tab** ([components/Calls/CallsStatsView.tsx](app/src/components/Calls/CallsStatsView.tsx), [components/Calls/BarChart.tsx](app/src/components/Calls/BarChart.tsx), [utils/callStats.ts](app/src/utils/callStats.ts)) — a second view inside the Calls tab (`.calls-mode-switch`, same List/Grid-toggle pattern as `CalendarView`), showing KPI cards (dials, answered, answer rate, talk time) and a per-day bar chart for a Week/Month period. Exists because Zadarma's own statistics don't stay available forever — the user's own experience was that they eventually age out — so the point isn't just a nicer view of live data, it's a **local, permanent copy** that survives whatever Zadarma's retention window turns out to be. Deliberately excludes recordings/transcripts (`CallStatRecord` in `utils/callStats.ts` keeps only `call_id, callstart, seconds, disposition, otherParty`) — this is a numbers view, not a call log.

- **Where the local history comes from**: `db.ts`'s `callStats` IndexedDB store (`DB_VERSION` 4), fed two ways — every manual "Load calls" upserts whatever it fetched (`fetchCalls` in `useCallsStore.ts`), and a background `syncCallHistory()` action runs once per Calls-tab mount to backfill/catch up automatically. The watermark for "what's already synced" is *derived* from the data itself (`getLatestCallStatDate()` = the max `callstart` already saved), not tracked as a separate key — a manual load for some arbitrary past range still correctly advances it if that happens to be the most recent date seen, with zero extra bookkeeping.
- **Backfill chunking**: a first-ever sync (no local history at all) reaches back 90 days — directly matching the user's own understanding of Zadarma's retention window, i.e. "save it before it's gone" is the literal reason this number was chosen, not a generic default. Split into ≤31-day chunks (`buildBackfillChunks`, matching the server's own per-request cap) and fetched **sequentially**, with the same 7-second spacing as the manual "Load calls" cooldown, for the identical rate-limit reason. `SYNC_RETRY_GAP_MS` (60s) additionally guards against re-running the whole sequence every time the user flips back to the Calls tab within the same minute — ordinary tab-switching isn't a signal that history needs re-syncing.
- **`CallsView`'s mount effect kicks off *two* independent things that both hit the same 10-req/min-capped endpoint** — the existing today-only list `load()` and this feature's `syncCallHistory()` — and they needed deliberate separation twice over, not once, to avoid tripping the limit before the user does anything at all (a real, reported bug: the rate-limit toast appearing on a tab that had just been opened). First, `syncCallHistory()` is started via a 7-second `setTimeout`, not called in the same instant as `load()`, so the two requests are spaced the same as any other two Zadarma calls in this app. Second, and less obviously: `load()` itself fires a fetch *synchronously* the moment the mount effect body runs, not deferred behind a promise — so React StrictMode's dev-only mount→cleanup→mount double-invoke (deliberate, to help catch missing-cleanup bugs) called it *twice* in the same synchronous tick, both times seeing `cooldown === 0` (the first call's `setCooldown(7)` hadn't re-rendered yet when the second call checked it), firing two real requests for what looked like one page open. Fixed with a `hasAutoLoadedRef` guard around `load()` specifically — a ref survives StrictMode's simulated unmount (the fiber isn't actually torn down) but correctly resets on a genuine remount later (leaving the Calls tab and coming back really does unmount `CallsView`), so it suppresses only the fake double-fire. `syncCallHistory()`'s own `setTimeout` didn't need the same ref treatment — the throwaway invocation's `clearTimeout` in its cleanup already cancels its own timer before it can fire, which is inherently StrictMode-safe without extra guarding.
- **On a chunk failure, the whole sync stops rather than skipping ahead to the next chunk.** This looks over-cautious but isn't: skipping would let a *later* chunk succeed and advance the id-derived watermark past a chunk that never actually synced, silently baking a permanent, invisible gap into "resume from the watermark" — a gap that nothing would ever go back and fill, since the watermark logic has no way to know it's not contiguous. Stopping means the watermark always accurately means "synced continuously up to here, nothing missing before it," at the cost of a rate-limited account needing a few separate tab visits to fully catch up after being away a long time (90 days ÷ 31-day chunks = 3 requests minimum for a cold start, more if any of them hit the rate limit and have to resume next visit). `CallsStatsView` shows an explicit "Local history synced through {date} — still catching up" note (gated on the latest locally-synced date being more than a day behind today) specifically so a stretch of zeros right after first opening this view reads as "still loading," not "no calls made."
- **The bar chart is hand-rolled SVG** (`BarChart.tsx`), not a charting library — a fixed logical `viewBox` (600×160) scaled to the container's real width via `preserveAspectRatio="none"`, one `<rect>` pair per day (a muted "total dials" bar with a narrower accent-colored "answered" overlay drawn from the same baseline, so the two numbers read as one glance per bar instead of needing a legend to cross-reference two series), native `<title>` tooltips carrying the exact per-day numbers so the x-axis labels can stay sparse (every 5th day for a month-length view; all of them for a week) without losing precision on hover. Chosen deliberately over a library like recharts to keep the bundle light, matching how the rest of this app avoids heavy UI dependencies — the whole feature (store logic, IndexedDB layer, stats view, chart) added about 8KB gzipped to the production build.
- **A real, live-reproduced bug worth remembering if any date-math in this file (or `useCallsStore.ts`'s chunk builder) is ever touched again**: the original `addDays()` constructed via `new Date(dateString + 'T00:00:00')` (parsed as *local* midnight) but read the result back out through `.toISOString()` (always UTC). In any positive-UTC-offset timezone, advancing by a day and re-extracting the date string could land back on the exact same calendar date instead of the next one — not just an off-by-one, but a value that could fail to advance at all under `+N` day arithmetic. Every loop in this feature (`bucketByDay`, `buildBackfillChunks`, the Statistics view's own week/month prev-next navigation) advances a date with this function, so a version that can return its own input unchanged for "+1 day" doesn't just miscount — it never terminates. This was caught by literally reproducing it: the Calls tab going fully unresponsive (not even answering a screenshot request) the moment it tried to mount and run the background sync. Fixed by anchoring every step — construction, arithmetic, and extraction — to UTC throughout (`toUtcDate()`/`setUTCDate()`/`getUTCDay()`/`getUTCMonth()` in `utils/callStats.ts`), so local timezone never enters the picture for date *arithmetic* at all (it's still used, correctly, for things that should genuinely reflect the user's wall-clock day, like `todayDateString()` and `CallsStatsView`'s own `rangeTitle()` display formatting — those aren't part of any loop, so the mismatch that broke `addDays()` doesn't apply to them).

## SMS inbox & webhook (`server/src/smsInbox/`, `app/src/components/Calls/SmsInboxView.tsx`)

**Why incoming SMS needs its own webhook, and why that webhook needed a second, separate route.** Zadarma's API (`sendSms()` in `server/src/zadarma.ts`) can *send* an SMS but has no method to list sent messages after the fact or to fetch incoming ones — the only way this app ever learns an SMS arrived is Zadarma pushing it to a webhook URL registered on the account. Registering that URL (`POST /api/zadarma/setup-sms-webhook`, an authenticated, one-time action triggered by the "⚙️ Registruoti SMS webhook" button in the SMS tab, needs `PUBLIC_BASE_URL` set in `server/.env`) isn't a plain `POST /v1/pbx/webhooks/url/` call, though — Zadarma first does its own `GET` against the candidate URL with a `zd_echo` query param and requires the response body to be exactly that value, verbatim (confirmed directly with Zadarma support; their own example is literally `exit($_GET['zd_echo'])`). This handshake and the actual SMS payload are deliberately two different, both-public routes on the same path: `GET /api/zadarma/sms-webhook` (the verification echo) and `POST /api/zadarma/sms-webhook` (the real event) — both sit *before* `app.use(requireAuth)` in `server/src/index.ts`, same as `/health` and `/api/apollo/webhook`, since Zadarma calls these directly and can't carry a session token.

**The incoming-SMS payload shape is genuinely undocumented, so the receiver is deliberately defensive rather than strict.** Zadarma's own official PHP reference client (`github.com/zadarma/user-api-v1`) has a dedicated event class for every other webhook type (call start/end/answer/record/...) — each with its own known field names and its own per-event-type signed-string composition — but no SMS event class at all. Zadarma support confirmed the webhook exists but couldn't point to field-name documentation. `POST /api/zadarma/sms-webhook` (`server/src/index.ts`) responds to this by never rejecting on an unrecognized shape: it best-effort-extracts `fromNumber`/`toNumber`/`message` by checking Zadarma's known call-webhook field names first (`caller_id`/`called_did`, from `NotifyStart`) then generic fallbacks (`from`/`to`/`sender`/`msisdn`/`text`/`message`/`destination`), but **always** saves the full raw body as JSON regardless of whether that guess succeeds — so the very first real incoming SMS can be inspected afterward (`raw_payload` in the DB) and the field-name guesses corrected without having lost the actual event. It also doesn't reject on a missing/unverifiable `Signature` header, for the same reason: `encodeSignature()`'s own algorithm (`base64(hmac-sha1(secret, signatureString))`) is known and already matches this file's own `sign()`, but `signatureString`'s *composition* is per-event-type and this SMS event isn't one of the types the official client actually implements, so there's nothing correct to check it against yet. This needed a second body parser registered: `app.use(express.urlencoded({ extended: true }))` alongside the existing `express.json()`, since Zadarma's webhook deliveries are form-encoded, not JSON (confirmed against the PHP client's `getWebhookEvent()`, which reads `$_POST`) — safe to add because each parser only engages for its own `Content-Type`.

**Persistence**: [server/src/smsInbox/db.ts](server/src/smsInbox/db.ts) — its own tiny `better-sqlite3` file (`server/sms-inbox.sqlite`, gitignored), separate from `linkedin.sqlite` even though both exist for the identical reason (a webhook/scheduled event can land whether or not a browser tab is open, so the durable copy has to live server-side, unlike every IndexedDB-only feature elsewhere in this app) — each server-side feature owns its own small file rather than sharing one multi-feature database. `incoming_sms` is insert-only (`insertIncomingSms`) — a webhook receipt is a fact, never edited afterward. `GET /api/sms-inbox` (authenticated) is the read side, polled/loaded by the frontend.

**The "Gaunamos SMS" tab merges incoming (server-side) and outgoing (this app's own send log, IndexedDB) into one threaded view**, on explicit request ("достать историю всех смс" — get the history of all SMS). [components/Calls/SmsInboxView.tsx](app/src/components/Calls/SmsInboxView.tsx) groups both into `Thread`s keyed by `phoneMatchKey()` — the same last-7-digits suffix-match helper the Calls tab already uses to link a call to a CRM row, reused here for the identical "numbers show up formatted wildly differently" reason. A thread whose key can't be derived (no parseable phone) falls back to a literal `__unknown__` bucket rather than being dropped. Each thread can expand to show its full entry history (newest first) and, if it matches a known contact or row (`phoneToRow`/`phoneToContact`, passed down from wherever `App.tsx` already computes these for the Calls tab), a "🏢 {label} →" jump button using the same cross-tab-navigation plumbing as everywhere else.

**Sending SMS from this tab directly (not just from a Contacts cell) was the other half of the same request** ("хочу чтоб я мог не только в контактах писать но и тут тоже"). `SmsComposeForm` is one shared component used two ways: inline inside an expanded thread ("↩ Atsakyti", phone pre-filled and locked) and as a fresh "✉️ Nauja SMS" compose box (phone field editable) — both go through the same `confirmDialog()`-gated send-then-log flow `CellHoverEditor`'s contact-list SMS button already established (a real, irreversible external action, so it needs the same explicit-confirm treatment as click-to-call). The outgoing log entry (`SmsLogRecord`, IndexedDB via `saveSmsLogEntry`) is written **regardless of success or failure** — a failed send still needs a visible record of "this was attempted and didn't go through," not just silence — because unlike incoming SMS (which Zadarma pushes) there is no Zadarma endpoint at all to list sent messages after the fact, so this log is the *only* record of outgoing SMS this app has.

## LinkedIn Automation (`server/src/linkedin/` + `app/src/components/LinkedIn/`)

**The one fact that shapes this entire feature**: LinkedIn has no official API for personal connection requests or messaging. Every other integration in this app (Zadarma, Apollo, OpenAI, ElevenLabs) is a clean, ToS-compliant REST API call — this one is browser automation (Playwright) driving the user's own real, already-logged-in Chrome, against a platform whose ToS formally prohibits it. The user explicitly confirmed they understand and accept this risk for this one feature specifically; every design choice below exists to keep that risk as low as it can be (behave like a careful human, not defeat detection outright) — not to make the automation itself less real. `TZ_LinkedIn_Automation.md` (repo root) is the original spec this was built from; the saved implementation plan adapted it into MyDesk's existing "React frontend + `server/` for anything the browser can't do safely" split rather than the spec's standalone-Electron-app framing.

**This is the first (and so far only) MyDesk feature where `server/` holds real, durable, server-side state** — every other feature persists purely in the browser's IndexedDB, because `server/` had otherwise been a stateless proxy. That doesn't work here: a scheduled sequence step has to fire at, say, 10:32am whether or not a browser tab happens to be open, so the state has to live in the server process. [server/src/linkedin/db.ts](server/src/linkedin/db.ts) is a `better-sqlite3` file (`server/linkedin.sqlite`, gitignored) with tables straight from the TZ's own data model: `campaigns`, `leads`, `sequence_steps`, `actions_log`, `conversations`/`messages` (the Inbox — not in the TZ's minimal schema, added because a real inbox needs to group messages by thread, and "which lead" alone isn't enough since someone can message first without being a tracked lead in any campaign), `safety_state`, `settings`. **`deleteCampaign()` deliberately does not delete `actions_log` rows** — its FK uses `ON DELETE SET NULL`, not cascade, so the historical record of what actually happened survives a campaign being deleted; only `leads`/`sequence_steps` (scoped, disposable) get removed in the same transaction. better-sqlite3 enforces foreign keys by default (unlike raw SQLite), made explicit via `db.pragma('foreign_keys = ON')` after this was the actual cause of a real, reproduced `SQLITE_CONSTRAINT_FOREIGNKEY` blocking campaign deletion the first time a campaign with any logged action was deleted, before the `ON DELETE SET NULL` was added.

**`server/src/linkedin/page.ts` is the only file in this feature allowed to know LinkedIn's actual DOM/URL structure** — every other module calls a named function (`isLoggedIn()`, `sendConnectionRequest()`, `sendMessage()`, `withdrawConnectionRequest()`, `searchLeads()`, `listConversationThreads()`, `scrapeThreadMessages()`, `replyInThread()`) instead of touching a selector directly. This is deliberate: LinkedIn's markup will change repeatedly over this feature's lifetime, and isolating that knowledge means a UI change is a one-file fix instead of an archaeology dig through Campaign/Safety Engine logic that has no business knowing what a "Connect" button looks like. [server/src/linkedin/browser.ts](server/src/linkedin/browser.ts) never launches its own browser — `chromium.connectOverCDP()` only, attaching to Chrome the user launches themselves with `--remote-debugging-port=9222` (see the Commands section above for the required `--user-data-dir` caveat — current Chrome versions silently refuse to open the debug port on the default profile at all). This is the entire safety premise: a warm session with real cookies/history/fingerprint reads as a human, where a fresh automated profile is exactly what would read as a bot. `getLinkedInStatus()` (`page.ts`) reports one of four states — `connected` / `not_connected` (CDP unreachable) / `logged_out` / `checkpoint` (a CAPTCHA or identity-verification page) — the last two being just as good a reason to halt every automated action as an outright CAPTCHA, not only CAPTCHA specifically (an intentional broadening beyond the TZ's own narrower circuit-breaker description). `browser.ts` also holds the human-pacing primitives every real action routes through: `humanDelay()` (a jittered, roughly-triangular delay so pauses cluster around a plausible "thinking about it" midpoint instead of being uniform across the whole range), `humanMouseMove()` (multi-step cursor movement, not an instant jump), `humanType()` (per-character delay variance, not `fill()`'s even keystrokes) — none of this defeats detection outright, it just avoids the most mechanical, obvious tells.

**The Safety Engine** ([server/src/linkedin/safety.ts](server/src/linkedin/safety.ts)) is the one gate every real action passes through immediately before executing, re-checked at execution time (not earlier, when an action was merely found "due" — state can change between the two, e.g. another action in the same tick already used up the daily cap). It checks, in order: the pause switch, work hours, and daily/weekly caps for connects and messages separately (`dailyConnectCap`/`weeklyConnectCap`/`dailyMessageCap`/`weeklyMessageCap`) — every cap scaled down by a **warm-up multiplier** (`getWarmUpMultiplier()`) that ramps linearly from a configurable starting percentage up to 100% over a configurable number of days, anchored to when warm-up was first turned on, so a new or long-idle account starts small and grows into its real limits instead of running at full volume from day one. Every one of these numbers lives in the `settings` SQLite table, editable from the UI (Nustatymai sub-tab) rather than hardcoded constants — deliberately, since LinkedIn's own real-world enforcement thresholds will drift over time and shouldn't require a redeploy to adjust. **`manual_review_enabled` defaults to `true`** and is the single most safety-significant setting in this feature: with it on, the background scheduler tick (`runSchedulerTick()`, every 5 minutes, `server/src/index.ts`) never executes anything itself — it only refreshes the Pending Approval list `findDueActions()` feeds, and every real send happens from one explicit, per-item click (`POST /api/linkedin/scheduler/approve`) in `PendingApprovalPanel.tsx`. Turning it off is what makes the scheduler genuinely autonomous — a deliberate, understood step down from the default, not something that can happen by accident.

**The Scheduler** ([server/src/linkedin/scheduler.ts](server/src/linkedin/scheduler.ts)) computes what's "due" (`findDueActions()`) by walking every *active* campaign's leads, finding each lead's next un-completed sequence step (derived live from `actions_log` via `getLastCompletedStepOrder()` — never a separately tracked "current step" column, so the two can't drift out of sync with each other), and checking whether that step's `delayDays` has elapsed since the previous step's success. A `message`-type step never becomes due for a lead that isn't `'connected'` yet — nothing here currently promotes a lead to `'connected'` automatically except `inbox.ts`'s sync (below), so a message step silently waits until that happens, a known and documented gap rather than a bug. `executeAction()` applies `{{firstName}}`/`{{lastName}}`/`{{title}}`/`{{company}}` placeholder substitution (`applyLeadPlaceholders()`, splitting `lead.name` on its first space the same best-effort way `utils/contacts.ts`'s `contactTextToFields()` does on the frontend) as a free personalization floor on *every* send, with an optional `overrideMessage` (the Pending Approval panel's AI-personalized/hand-edited text) replacing it entirely when supplied. **A real, shipped bug found and fixed this session**: the connect-step call to `sendConnectionRequest()` originally passed no note argument at all, so connect requests never carried their configured note text regardless of what a connect step's template held — fixed by actually threading `resolvedText` through.

**Stale-invite withdrawal is deliberately excluded from the background auto-execute path, even with manual review off.** `findStaleInvites()`/`withdrawInvite()` (same file) surface every lead still `'pending'` at least N days after its connect was sent, across every campaign regardless of campaign status — but withdrawing is only ever triggered from an explicit per-lead button in `StaleInvitesPanel.tsx`, never from `runSchedulerTick()`. The reasoning, spelled out in the code: withdrawing is a real LinkedIn action with its own risk profile this feature has no field experience with yet, and "manual review off" was an opt-in the user made specifically about *outreach* sends — it shouldn't silently also start firing a category of action they never separately agreed to. `'withdrawn'` is its own lead status (distinct from `'skipped'`, which means the user deliberately chose not to pursue a lead at all from the Pending Approval panel) — both permanently stop a lead's sequence, but collapsing them into one status would lose *why* a lead stopped when reviewing history later. Both `findDueActions()` and `getCampaignStepBreakdown()` (analytics) need to exclude `'withdrawn'` leads the same way they already exclude `'skipped'` ones — a real gap where only the latter was originally handled, caught and fixed during this session's own review before it shipped as a bug.

**The Inbox** ([server/src/linkedin/inbox.ts](server/src/linkedin/inbox.ts), synced every 10 minutes via its own background interval in `index.ts`, separate from the Scheduler's 5-minute one since they're different concerns — read/reconcile vs. write/send — and less frequent specifically so this doesn't become the thing that burns through the account's "looks human" budget on its own) does two things nothing else in this codebase can: **promotes a `'pending'` lead to `'connected'`** the moment a real conversation with them exists (LinkedIn only allows messaging a 1st-degree connection, so a conversation existing at all is proof the invite was accepted — this is what actually unblocks a campaign's `message` steps for that lead), and **auto-marks a lead `'replied'` the instant a genuine inbound message is detected**, which permanently stops the Scheduler from ever touching that lead again. This "auto-stop on reply" isn't just a nicety — the TZ frames it as ethically load-bearing (a lead who's actually engaged should be handled by a human from that point on, not kept in an automated sequence) and this is the mechanism that enforces it. Since LinkedIn's DOM gives no cheap "only what's new" cursor, `scrapeThreadMessages()` always re-scrapes a thread's full currently-visible history on every sync; `addMessageIfNew()` (`db.ts`) is what prevents that from creating duplicate rows — its dedup key tolerates up to a minute of drift on `sent_at`, since LinkedIn's own displayed timestamps are relative ("2m", "Yesterday") and only approximately parseable, not exact.

**Analytics** ([server/src/linkedin/analytics.ts](server/src/linkedin/analytics.ts)) has two layers beyond the overall sent/accepted/replied funnel: a per-campaign, per-step breakdown (`getCampaignStepBreakdown()`) that distinguishes **`waiting`** (correctly positioned for a step and actually eligible right now) from **`blocked`** (positioned for a `message` step but not yet `'connected'`, so it can't actually fire regardless of sequencing) — a real analytics inaccuracy found and fixed this session, since without the split a `'pending'`-not-yet-`'connected'` lead read as "about to get their follow-up" when `findDueActions()` would never actually consider them yet — and a 30-day daily activity chart (`getDailyActivity()`, aggregated from `actions_log`, forward-filled so a quiet day shows as zero rather than a gap) rendered as hand-rolled SVG bars (`LinkedInActivityChart.tsx`), the same "no charting library, keep the bundle light" approach `CallsStatsView`'s own `BarChart.tsx` already uses. Both day-bucketing helpers anchor construction/arithmetic/extraction to UTC throughout (`dayKeyUtc()`), deliberately avoiding the exact local-time/UTC-mixing bug documented above for `utils/callStats.ts`'s original `addDays()`.

**AI features go through `server/src/openai.ts`, same `gpt-4o-mini` + typed-error-class pattern as every other AI call in this app** (`parseContactText`, `summarizeCall`): `personalizeLinkedInMessage()` (light rewrite of a placeholder-substituted template, never translating, connect notes hard-capped at LinkedIn's own 300-character limit post-hoc) and `suggestLinkedInReply()` (drafts an inbox reply matching the conversation's own language, instructed never to fabricate facts not present in the message history). Both are strictly "AI drafts, human reviews" — `POST /api/linkedin/personalize` returns `{baseText, personalizedText}` without sending anything, landing in `PendingApprovalPanel.tsx`'s editable textarea for review/edit before an explicit "✅ Approve" actually sends it (as `overrideMessage`); `POST /api/linkedin/inbox/:id/suggest-reply` similarly only fills `InboxPanel.tsx`'s reply draft, never auto-sends.

**Every per-row async action in the frontend stores use a `Set<string>` of in-flight keys, not a single `string | null`** (`useLinkedInCampaignsStore.ts`'s `approvingKeys`/`personalizingKeys`/`withdrawingKeys`) — this is a real, safety-significant fix made during this session's own review, not the original shape. A single shared key meant clicking a second row's action button while a first was still in-flight made the *first* row's button appear re-enabled (the shared key had moved to the second row), risking a real duplicate LinkedIn send if clicked again before the server-side status update landed. Verified live with two concurrent requests, each correctly resolving with its own row's data and no cross-contamination. This is the same pattern `useCallsStore.ts`'s `transcribingIds`/`summarizingIds` and `ApolloContactSearchModal.tsx`'s `addingPersonIds` already used correctly elsewhere in this app — if you add a new per-list-item async action anywhere, use a `Set`/`Record` keyed by item id, not a single "current key," whenever more than one item can plausibly be acted on concurrently.

**`InboxPanel.tsx`'s AI-suggest-reply flow has the same stale-async-response race this codebase already guards against elsewhere** (Apollo's phone-reveal poll, `SocialLookupModal`'s `cancelled` flag): switching to a different conversation while a suggestion request is still in flight could otherwise let the old conversation's result land in the new conversation's reply box. Fixed by capturing the conversation id at request time and re-checking it against `useLinkedInInboxStore.getState().openConversationId` before applying the result, plus a `useEffect` that resets the draft on every conversation switch — verified live with two synthetic conversations that the stale suggestion never appears, even 4+ seconds after switching away.

**`withdrawConnectionRequest()` (`page.ts`) finds its target row by looping through the sent-invitations list and comparing each row's own link `href` in plain JS**, not by interpolating `profileUrl` into a CSS attribute selector (`[href*="..."]`) — `profileUrl` originates from this app's own stored lead data (CSV import, manual entry, or the search scraper), and a selector built by string interpolation is a real, if narrow, injection surface if that string ever contained a stray `"`. `searchLeads()`/`listConversationThreads()` already used this loop-and-compare-in-JS shape for unrelated reasons; `withdrawConnectionRequest()` was fixed to match during this session's review.

**`isLoggedIn()` took two real, live-reproduced fixes in the same session before it was actually right — both found only by attaching to a genuinely logged-in session and looking, never by guessing.** The original selector checked for `#global-nav` and `[data-control-name="identity_welcome_message"]`, both of which LinkedIn has since removed: the current nav has no `#global-nav` id at all, and the whole header now uses hashed, build-specific CSS class names (e.g. `_3bdeafd6`) instead of the old semantic ones — a real, freshly-logged-in session (feed loading correctly, profile visible, nav fully present) was confirmed reporting as `logged_out`. First fix: check `#primaryNavLinksComponentRef a[href*="/messaging/"]` — a URL *path*, not a class name, so it survives a markup rebuild. That worked on the feed page, but broke a *second* way that only showed up by testing a different route: LinkedIn's `/messaging/` pages don't render nav inside `#primaryNavLinksComponentRef` at all — a different sub-layout entirely — so the scoped selector reported a real, logged-in session on its *own messaging inbox* as logged out. This isn't a corner case: `listConversationThreads()`/`scrapeThreadMessages()` (the Inbox sync) call `isLoggedIn()` on exactly that route, every single sync — the scoped version would have silently broken Inbox sync permanently while still working everywhere else, a particularly nasty way for a regression to hide. Final fix: drop the container scoping entirely and just check `a[href*="/messaging/"]` anywhere on the page — a stray `/messaging/` link on a genuinely logged-out marketing/login page isn't a realistic false positive, that path only exists in the logged-in product surface. **The lesson that generalizes**: when "fixing" a selector against a single confirmed page (here, the feed), also check it against whatever *other* routes the same function gets called from before considering it done — a fix that only works on the page you happened to test it on isn't yet a fix.

**A real imported lead list turned out to be mostly existing connections, not new prospects — and the fix that came out of investigating it is worth understanding if `findDueActions()`/`executeAction()` are ever touched again.** A 237-person list, once actually run through the (already-live-verified) send pipeline with manual review off, failed 45+ times in a row with the exact same error: `sendConnectionRequest()`'s "No Connect button found on this profile" — because LinkedIn genuinely shows no Connect button for a profile you're already a 1st-degree connection with (it shows "Message" instead), confirmed by hand on several of the failed URLs (real "· 1st" badges, real "500+ connections", real "Message" buttons). **The tempting first instinct — bulk pre-scan every lead's profile to sort "prospect" from "already connected" before sending anything — was tried and deliberately abandoned**: scanning 237 profiles back-to-back (even read-only, nothing sent) is itself an unusual, bot-like volume/pattern separate from whatever gets sent, and the live attempt at it actually crashed a Chrome tab partway through *and* showed a rising rate of ambiguous results as it went — plausibly LinkedIn's own pages slowing down/degrading under the rapid-navigation pattern, though not conclusively proven either way. That data point alone is reason enough to avoid a dedicated bulk-scanning pass as a general technique in this feature. **The actual fix**: let "already connected" be discovered the same way it already was — as a normal, individually-paced side effect of the real connect attempts the campaign was going to make anyway, which are already safely rate-limited by the existing daily cap and warm-up ramp. `getLastActionForLeadStep(leadId, stepId)` (`db.ts`) plus `isNoConnectButtonError()` (`scheduler.ts`, an exact string match on `sendConnectionRequest()`'s own error text) make `findDueActions()` skip re-offering a connect step for a lead whose most recent attempt at that *exact* step already failed this exact way — without ever mutating `lead.status`. Status was deliberately left alone rather than auto-setting it to `'connected'` (which would also unlock message-step eligibility): if this exact error string ever starts firing for an unrelated reason — a real risk, given LinkedIn's own selectors have broken twice already this session — auto-relabeling would silently misclassify a genuine prospect as already-connected, permanently losing them from ever getting a real attempt. The narrower, data-driven skip (checked per lead+step from what's already logged, nothing inferred) accepts a few possible extra retries as the safer failure mode over a wrong permanent label.

**That caution turned out to be justified — the "no Connect button" signal itself was significantly unreliable, for a completely different reason than "this person is already connected."** Following up directly on the account owner's own live correction ("I know that person isn't in my contacts"), inspecting the actual DOM (not guessing) found the real root cause: LinkedIn's current Connect control is an `<a>` element with `aria-label="Invite {name} to connect"` — **not a `<button>` at all** — with hashed, build-specific CSS classes, the same markup-instability pattern documented elsewhere in this file for `isLoggedIn()`'s own nav selector. `sendConnectionRequest()`'s old selector (`button:has-text("Connect"), button[aria-label*="Connect" i]`) only ever matched `<button>` elements, so it silently reported "no Connect button" on **every single profile**, real prospects included — not just the genuinely-already-connected ones. This means the 91 leads `findDueActions()` had already excluded via the fix above are not a clean "confirmed already connected" set — some real, unattempted prospects are almost certainly sitting in there too, wrongly skipped by a detection bug rather than correctly skipped for being real duds. Fixed by matching `[aria-label*="to connect" i]` regardless of element tag — a selector describing intent, not markup, so (like the `isLoggedIn()` fix) it survives both a tag-type change and a display-language change. If this list is ever revisited, the honest thing to do is re-offer those 91 for a fresh attempt now that detection is fixed, not treat the old skip list as ground truth.

**Two more real bugs surfaced getting an actual successful send working end-to-end, both about how the Connect element gets clicked once correctly found, not about finding it:**
1. **`click({ force: true })` doesn't do what it sounds like it does.** The first fix attempt for "subtree intercepts pointer events" (an unrelated decorative icon sitting over the same screen coordinates) was `force: true` — but that only skips Playwright's own pre-click actionability checks; the actual click is still dispatched at real screen coordinates, so it can still land on whatever the browser's own hit-testing finds there. Confirmed live and firsthand, this is not a theoretical risk: it navigated the automation tab to **LinkedIn's own Campaign Manager** (`/campaignmanager/accounts?...`), apparently by landing on an ad-related icon instead of the Connect link beneath it — a real, unintended side effect, not just a failed click. Nothing was clicked on that page afterward and it was navigated away from immediately, but it's a clear illustration that `force: true` is not a safe substitute for "I've already confirmed this is the right element" when something else is genuinely overlapping it on screen.
2. **The actual fix: `connectButton.evaluate((el) => el.click())`** — a real DOM click dispatched directly on the already-confirmed-correct element (via its `aria-label`), bypassing screen-coordinate hit-testing entirely, so there's nothing else on the page it can land on instead. This is the one place in this feature that intentionally departs from "simulate a real mouse click" for human-pacing reasons — justified specifically because the alternative (coordinate-based clicking) had just been shown to click the wrong thing.

Once both fixes landed, a real end-to-end send was verified three independent ways: the API call returned `{"ok": true}`, the profile's own button flipped from "Connect" to "🕐 Pending" on reload, and LinkedIn's own `/mynetwork/invitation-manager/sent/` page showed the entry with the exact note text sent (`"Labas, malonu susijungti!"`) — confirming the note-attachment path (`button:has-text("Add a note")` → `textarea[name="message"]` → `button:has-text("Send")`) also worked correctly once the initial Connect click actually landed right, without needing changes of its own.

**A second real bug, found by noticing 4 duplicate log rows where none should exist**: `runSchedulerTick()` had no protection against running twice concurrently. The background 5-minute interval (`index.ts`) and a manually-triggered `POST /api/linkedin/scheduler/run` landed close enough together in real testing that both executed at once — each computed its own `findDueActions()` snapshot before either had recorded a result, so both independently attempted several of the same leads (confirmed via `SELECT lead_id, COUNT(*) ... GROUP BY lead_id HAVING n > 1` turning up exactly 4 leads logged twice). Harmless *this* time (both hit the same already-terminal error), but the identical race could just as easily let two overlapping ticks both pass `canSendConnect()`'s cap check before either call `recordConnectSent()` — momentarily exceeding the daily cap — or, worse, both fire a real connect at the same person within moments of each other. Fixed with a module-level `tickInProgress` boolean lock around the whole function body (single Node process, no multi-worker deployment, so this is sufficient — no need for anything heavier like a DB-backed lock): a tick that finds one already running just no-ops (`skippedConcurrent: true`) rather than queuing or blocking, since the next tick or manual trigger picks up whatever's still actually due anyway.

**A separate, real setup gotcha found in the same live-verification pass, unrelated to LinkedIn's own markup**: current Chrome (confirmed on 151.x) silently refuses to open the remote-debugging port at all when launched against the *default* profile — no error, the port just never listens, which looks identical to "Chrome isn't running yet" from this app's side. This is deliberate Chrome hardening against outside tools attaching to a user's main, cookie-holding session. The fix is a **separate, dedicated `--user-data-dir`** (not a copy of the default profile) — see the Commands section above for the exact launch command. That profile starts empty and needs a one-time manual LinkedIn login in it; reusing the *same* directory on every future launch is what keeps it a real, warm, persistent session afterward rather than a fresh one each run. A related gotcha, also confirmed live: if the user's *regular* Chrome (any profile) happens to already be running at all when the automation profile needs (re-)launching, a plain `open -a` just opens a new window in that already-running instance and silently ignores the new `--args` — Chrome only applies command-line flags on the app's first launch, not to a request routed to an already-running instance. `open -na` (the `-n` forces a genuinely separate process) is required whenever there's any chance another Chrome window is already open, which in practice is most of the time — this bit a real relaunch after the automation Chrome window had closed on its own (see below) while the user's normal Chrome was still running.

**Two real bugs found during this session's first live-fire test of manual-review-off autonomous sending, both worth understanding if `runSchedulerTick()`/`canSendConnect()` are ever touched again.** With manual review off (an explicit, deliberate choice — see safety.ts's own doc comment), the background 5-minute tick is the only thing standing between "rate-limited autonomous sending" and unattended trouble, so both of these mattered more than they would have under manual review, where a human reviews every item before it fires:

1. **Only *successful* sends count against the daily/weekly caps** — `recordConnectSent()`/`recordMessageSent()` are only called after a real send succeeds, so a *failed* attempt (see the "no Connect button" scenario documented above) never counts against `canSendConnect()`'s cap at all. That's fine when failures are rare, but turns into a real problem the moment a chunk of a lead list is duds: confirmed live, a single automatic 5-minute tick made **41 real profile page-view attempts in under 3 minutes** against a list that was mostly already-existing connections — nothing was stopping the loop from working through dozens of leads in one go, since none of the failures ever tripped the success-only cap. Every one of those 41 was a real page load against the real account, regardless of outcome. Fixed in two layers, both still in place: `MAX_ATTEMPTS_PER_TICK` (`scheduler.ts`, currently 5) caps attempts within a single tick, and — added right after, on the account owner's own explicit instruction, since a per-tick cap alone doesn't bound the *daily* total if the tick just runs again every 5 minutes — `canSendConnect()` (`safety.ts`) now also checks a real **daily attempt ceiling** (`DAILY_ATTEMPT_CAP_MULTIPLIER = 2.5`, i.e. at today's cap of 4 successful connects, at most 10 total profile checks per day regardless of outcome), tracked via `safety_state.profile_views` — a column that already existed in the schema from the original TZ data model but had never been wired up to anything until this fix, repurposed here rather than adding a new one. `recordConnectAttempt()` is called unconditionally the moment `canSendConnect()` passes, *before* the real send is attempted, so it counts regardless of what happens next. Surfaced in the frontend too (`attemptsToday`/`dailyAttemptCap` in `LinkedInSafetySnapshot`, shown in `LinkedInView.tsx`'s safety bar as "👀 Patikrinta šiandien") — this codebase already has one prior instance of a safety-relevant server field existing but not being shown in the UI (see the message-cap gap documented above), worth not repeating. The lesson: any cap that only counts one *outcome* of an action can be silently bypassed by an action that reliably produces the *other* outcome — a cap needs to bound the attempt itself if the attempt alone has a real-world cost (here: a page view LinkedIn can see), not just the outcome you were trying to limit.
2. **The Chrome window (automation profile) and the `server/` Node process can both die independently, silently, with no alert** — confirmed live: both were found dead (Chrome window closed, `npm run dev` process gone) with no error surfaced anywhere, discovered only because a routine status check came back empty/refused. Given this feature is explicitly meant to run unattended for stretches, a silent process death is a real gap — the current state of the codebase does not yet auto-restart either one or alert on it; anyone relying on unattended operation should periodically verify `GET /api/linkedin/status` returns `connected` rather than assuming a resumed campaign is actually still running. Worth a real fix (a process supervisor, a health-check alert) if genuinely unattended operation becomes a firm requirement rather than an occasional convenience.

**Frontend structure**: [components/LinkedIn/LinkedInView.tsx](app/src/components/LinkedIn/LinkedInView.tsx) is the tab's shell — connection status, an always-visible "⏸ Sustabdyti viską" pause button (deliberately not buried in Settings, since the whole premise of a kill switch is not having to go dig for it once something looks off), a live safety summary bar (today/this-week counts against effective, warm-up-scaled caps, for both connects and messages), and a sub-nav: **Kampanijos** (`CampaignsPanel.tsx`/`CampaignDetail.tsx` — campaign/lead/sequence-step CRUD, CSV import via `LeadCsvImport.tsx`, LinkedIn-search-based import via `LeadSearchImport.tsx`, CSV export), **Pokalbiai** (`InboxPanel.tsx` — the synced Inbox, reply + AI-suggest-reply), **📊 Analitika** (`AnalyticsPanel.tsx`), **🕐 Užstrigę** (`StaleInvitesPanel.tsx`), **Testas** (the original Phase-0 single manual test-connect action, kept alongside the full Campaign Engine rather than removed, still useful for a one-off connect outside any campaign), and **⚙️ Nustatymai** (the Safety Engine settings form). Two independent stores split state the same way `useWorkspaceStore`/`useTableStore` split table state elsewhere in this app: `useLinkedInStore.ts` (status/safety/pause/the Testas tab's single test action) and `useLinkedInCampaignsStore.ts` (campaigns/leads/steps/pending-approval/stale-invites) plus `useLinkedInInboxStore.ts` (conversations/messages/AI-suggest).
